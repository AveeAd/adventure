# UI internationalization

UI-language i18n, resolved to a settled scope: **English only, but i18n-ready** — wire the library, extract every UI string to a catalogue, ship only the `en` locale. Translation labour is deferred; the refactor is not. Companion to FEATURE.md §7 (the public site's SSR/SEO constraints this must respect) and §9 (the `Notification.message` blocker this inherits). Depends on nothing else being built first.

**Status**: built (Milestone 2 Phase 18 — see FEATURE.md §1). The library, catalogue layout, locale persistence, AntD locale, the full Intl-formatting bug fix, and the string extraction itself are all live — every route and component in both apps, including route `<title>`s, now reads UI copy from a catalogue rather than a hardcoded literal. See "What's actually extracted" below.

## Scope

Removes the *technical* blocker named in FEATURE.md §1/§11 ("needs a scoping decision... before any library gets wired in") without answering the product question of which second language ships or how it gets translated — those stay open by design (see Open decisions).

In scope: translatable UI chrome (nav, buttons, form labels, empty states, badges, route titles) across both `apps/public` and `apps/admin`, plus locale-aware date/number/currency formatting (which fixes a live SSR hydration bug independent of i18n). Out of scope, permanently: user-generated content (page titles, Markdown, trip reports, trail/spot names) — this is a wiki, and a Nepali-language description of a route is a different page with its own authors, not a translation of an English one.

## What's actually extracted (as built)

Every route and component in both apps is converted — this section is now a completion record, not a partial-split disclosure.

- The library, both apps' catalogue layout, `i18nProvider` wiring (admin), locale-cookie resolution (public), AntD `locale` prop, `<html lang>` wiring.
- The Intl-based date/time formatting fix — **all 20** bare `toLocaleDateString()`/`toLocaleString()` call sites across both apps now go through `lib/format.ts`'s `formatDate`/`formatDateTime` (a real SSR-hydration-class bug, independent of translation).
- Both named "natural first extraction" enum-label maps: `STATUS_LABEL` (now `common:status.*`) and `RATE_UNIT_LABELS` (now `common:rateUnit.*`).
- `GuideProfile.currency` — added, migrated, wired through the DTO/service/all UI sites, closing the data-model gap this doc originally flagged.
- The raw-concatenation currency bug (`{report.currency} {report.actualCostAmount}`) — fixed via `formatCurrency`.
- **`apps/public`** — all routes converted: `__root.tsx`, the Discover home page, guide directory/profile, every adventure-page route (create/edit, trail/spot new forms, the full page view and all its sub-sections — stories, gallery, trails & spots, see-also, contribute/edit), every history/diff page (page, trail, and spot revisions), trip groups (list/detail/new), trip reports (detail + threaded comments), activity tracks (list/detail/upload), account pages (guide-profile, contributor profile, login, auth callback). Namespaces: `common`, `discover`, `guides`, `adventurePage`, `groups`, `tripReports`, `account` — all seven now exist and are registered in `lib/i18n/index.ts`.
- Route `<title>`s — all `head()` calls across both apps now resolve through the shared `i18next` instance's `.t()` (called directly, not via the `useTranslation` hook, since `head()` runs outside component context) rather than a hardcoded literal. Dynamic titles that interpolate user content (a page/trail/group/report's own title) keep that content untranslated by design — only the surrounding template text ("Edit ", "History — ", "v{{version}} — ") is a catalogue key.
- **`apps/admin`** — all resource files converted: master-data list/form/create/edit (field labels keyed by field name via `resources:fields.*`, replacing `config.ts`'s inline labels at the display layer rather than restructuring `config.ts` itself), every Show/List/Edit page (adventure pages, trails, spots, trip groups, trip reports, guide profiles, users, activity tracks), the three Province/District/Municipality location resources, shared components (`GeodataHistory`, `VerificationStatusControl`, `AppTitle`, `GeometryMap`), `Login.tsx`, and `App.tsx`/`Dashboard.tsx` (already done previously). `AuthCallback.tsx` needed no changes — no user-facing text.
- Master-data slug-as-translation-key fallback (recorded below as "approach settled") — still just a documented approach, not implemented; no master-data row currently needs a translated display label beyond its English `name` field.

## Library and catalogue layout

**`i18next` + `react-i18next` for both apps.** SSR-safe, framework-agnostic, and — decisively — Refine's `i18nProvider` contract is shaped around exactly i18next's `t`/`changeLanguage`, so `apps/admin` gets first-class integration for almost nothing. Rolling a hand-written string table would fit the repo's minimal-dependency character, but plurals and interpolation are where hand-rolled i18n reliably breaks once a second locale actually lands.

**Separate catalogues per app, not a shared `packages/i18n` workspace.** The root `package.json` declares `apps/*` only; a shared package means a new `packages/` tier plus build-order changes in `Dockerfile.dev`/`Dockerfile.prod` — real cost against near-zero benefit, since the two apps share almost no strings (admin is master-data CRUD labels, public is contributor-facing prose). Revisit only if overlap grows.

```
apps/public/src/locales/en/{common,discover,adventurePage,guides,groups,tripReports,account}.json
apps/admin/src/locales/en/{common,resources,dashboard}.json
```

**As built**: `apps/public` has all seven namespaces (`common`, `discover`, `guides`, `adventurePage`, `groups`, `tripReports`, `account`); `apps/admin` has all three (`common`, `resources`, `dashboard`) as designed. `apps/admin`'s `resources.json` grew per-resource `fields.*` sub-objects (e.g. `trails.fields.*`, `users.fields.*`) plus a couple of shared blocks (`geodataHistory.*`, `verification.*`) rather than splitting into more namespace files — kept the file count matching the original three-namespace design since the added key volume didn't justify a restructure.

Keys: `namespace:dot.separated.key`, e.g. `adventurePage:trailsAndSpots.heading`.

## What is in scope

Roughly 120 strings in `apps/public`, ~75 in `apps/admin`:

- Inline JSX text and `label`/`hint`/`placeholder`/`aria-label` props across 19 public routes and 15 components.
- **Route `<title>`s** — every route sets one via TanStack's `head:` (`head: () => ({ meta: [{ title: 'Guide directory' }] })`). Easy to miss, and SEO-relevant.
- The two existing enum-label maps, already string-table shaped and the natural first extraction: `RATE_UNIT_LABELS` in `apps/public/src/lib/format.ts` and `STATUS_LABEL` in `apps/public/src/components/Badge.tsx`.
- Admin: Refine resource `meta.label`s in `App.tsx` (~15), `apps/admin/src/resources/config.ts` (~30 — the most structured, cheapest to convert), `apps/admin/src/pages/Dashboard.tsx` (~31).
- AntD's own `ConfigProvider` gains a `locale` prop, currently absent, so pagination/empty-state/date-picker strings stop being hardcoded en_US.
- `<html lang>` in `apps/public/src/routes/__root.tsx` and `apps/admin/index.html` become locale-driven.

**Explicitly not translatable**: user-generated content — page titles and Markdown, trip reports, trail/spot names, group descriptions.

## Locale-aware formatting — the part with immediate value

Worth doing even at English-only, because it fixes a **live bug**: 20 bare `toLocaleDateString()`/`toLocaleString()` calls with no locale argument (13 at the time this doc was written, more by the time it was built — Phases 15-17 added routes with the same pattern), and zero `Intl.*` usage anywhere in the repo. Under SSR, the server formats with the *container's* locale and the client re-formats with the *visitor's* — server HTML and hydrated HTML can disagree, a hydration mismatch shipping today in both apps.

**Built**:
- Centralised in `apps/public/src/lib/format.ts` (already existed, already held `formatRateUnit`) with explicit `Intl.DateTimeFormat('en-US', opts)` — hardcoded to `en-US` rather than threaded from the UI locale, since only `en` ships; `formatDate`/`formatDateTime`/`formatCurrency`/`formatNumber` all take an explicit locale internally so the fix holds regardless. `apps/admin` got its own equivalent `lib/format.ts` (no SSR there — a Vite SPA — so no hydration mismatch to fix, but consistency with `apps/public` and with AntD's locale was worth it anyway). All 20 call sites across both apps now go through these helpers.
- Currency: the raw concatenation `{report.currency} {report.actualCostAmount}` now reads `formatCurrency(report.actualCostAmount, report.currency)`.
- **`GuideProfile.currency` was missing — added.** Schema, migration, DTO (`SUPPORTED_CURRENCIES` list mirroring `TripReport`'s), service, and all four UI sites (`guides/$id.tsx`, `guides/index.tsx`, `account/guide-profile.tsx`'s edit form, admin's `GuideProfileShow.tsx`) now read/write it instead of hardcoding `NPR`.
- Units stay baked into labels (`"Max altitude (m)"`, `${(v/1000).toFixed(1)} km`) — metric-only, no unit-conversion layer. Not touched, as designed.

## Locale and URL persistence

**No URL locale segment now.** With only `en` shipping, adding `/en/...` churns every route file for zero benefit, and there is no sitemap.xml, no robots.txt, no canonical tags anywhere in `apps/public` today — the SEO surface being protected is just `<title>` tags. The *intended* future strategy is recorded so the choice isn't re-opened blind: a **path prefix** (`/ne/...`), not cookie-only, because path-based is the only reliably indexable option, and SEO is the stated reason TanStack Start was chosen over Next.js in the first place.

Persistence: a cookie, resolved server-side in the root loader so SSR and client agree. **No `User.locale` column** — a public read-heavy site serves mostly anonymous visitors, for whom a per-user column does nothing.

**Built**: `apps/public/src/lib/i18n/locale.ts`'s `resolveLocale()` reads the `locale` cookie via `@tanstack/react-start/server`'s `getCookie()` server-side (dynamically imported, so the server-only boundary stays explicit, mirroring `lib/auth/api.ts`'s `isServer` split) and via `document.cookie` client-side, called from `__root.tsx`'s route `loader`. `SUPPORTED_LOCALES` has exactly one entry (`en`) today, so this always resolves to `en` — the mechanism is real and tested (confirmed `<html lang="en">` renders server-side), but there's nothing to actually switch between yet.

## The three known blockers — explicit positions

| Blocker | Position | Why |
|---|---|---|
| `Notification.message` precomputed strings | **Deferred** | FEATURE.md §9 already accepted this tradeoff. Migrating to `type` + `params Json` has zero user-visible benefit at English-only, and historical rows stay English regardless of when it happens. |
| ~46 API exception messages + class-validator defaults | **Out of scope** | The right fix is stable machine-readable error codes, not translated strings — a separate, bigger refactor. `apps/api/src/common/filters/http-exception.filter.ts` is the single choke point where codes would attach, if this is ever done. |
| Master-data display names (`ActivityType.name` et al.) | **Deferred, approach settled** | Every lookup table has a stable `slug` — slug-as-translation-key needs no migration. Master data is community-extensible from admin, so a new row will have no catalogue entry; any implementation must fall back to the DB `name`. Recorded now to prevent a `*_translations` table being invented later. |

One more, recorded for completeness: the full-text search trigger (FEATURE.md §9) hardcodes `to_tsvector('english', ...)`. A second *content* language would need a per-row `regconfig` or a second vector column — out of scope here since content language is a different axis from UI language, but worth writing down.
