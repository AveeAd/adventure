# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is right now

This is a **working monorepo**, not just design docs — `apps/api` (NestJS), `apps/admin` (React + Vite + Refine + Ant Design), and `apps/public` (TanStack Start) are all implemented and run together via `docker-compose up`. All of Phases 1–14 from FEATURE.md's roadmap summary are built: the public site has a real Tailwind-based visual identity, the admin dashboard has grown well beyond Phase 5's master-data CRUD (content moderation, user management, geodata moderation), trip-companion groups — the one pillar with no design doc through Phase 10 — is designed and built, the map/geodata layer has a public+admin UI, the content-enhancement grab-bag (tags, related pages, threaded replies, multi-currency costs, a stricter `rateUnit` enum) is done, and full-text search + in-app notifications are live. There's also a real deployment pipeline now — GitHub Actions + docker-compose + Caddy, not just local dev. The live `apps/api/prisma/schema.prisma` is the actual source of truth for the schema; there's no separate ER diagram artifact to keep in sync with it. Everything through Phase 14 + deployment is **Milestone 1, done**. Milestone 2 (FEATURE.md §1) phases the rest: **Phase 15, geodata changeset history (GEODATA_HISTORY.md), is built** — `TrailRevision`/`SpotRevision` full-snapshot history, revision-scoped `TrailConfirmation`/`SpotConfirmation`, diff/revert endpoints, and admin+public history UI are all live; the old service-layer "reset verification and delete confirmations on edit" rule described in FEATURE.md §4 is retired. **Phase 16, trail elevation + activity tracks (TRAIL_ELEVATION.md + ACTIVITY_TRACKS.md), is also built** — GPX/KML/KMZ/GeoJSON parsing (`apps/api/src/tracks/parsers/`), `TrailElevationProfile` + the geometry-conditional invalidation rule, the GPX-upload path in the trail-creation UI, `ActivityTrack` (import/create/update/delete, privacy-trimmed reads, cursor pagination), promote-to-trail, and admin+public UI are all live — with three pieces named-not-built rather than silently dropped: the `offline-bundle` endpoint (a mobile-only consumer, and mobile is out of scope), an `ST_DWithin` proximity query, and a public UI for `propose-trail-update` (the endpoint works; no existing-trail picker was built). **Phase 17, spatially-derived district tagging (FEATURE.md §4), is also built** — `District.boundary` (77 districts' real polygons imported via `import-district-boundaries.ts`, sourced from the `nepal-geojson` npm package rather than OSM/HDX directly, unioned+simplified into a ~410KB fixture), `ST_Intersects`/`ST_Contains` derivation firing from trail/spot create and geometry-update, and the required fix narrowing `AdventurePagesService.updateMetadata`'s district delete to `source: 'MANUAL'` (now an upsert, so a manual pick upgrades an existing `DERIVED` row instead of colliding with it) are all live. **Phase 18, UI i18n (I18N.md), is built** — `i18next`/`react-i18next` wired in both apps, the catalogue layout, cookie-based locale resolution, AntD's `locale` prop, and a real SSR-hydration-class bug fix (all 20 bare `toLocaleDateString`/`toLocaleString` call sites across both apps now go through explicit-locale `Intl` helpers) are all live, plus `GuideProfile.currency` (a data-model gap the pass surfaced) and both named enum-label maps. Every route and component in both apps — including all ~25 route `<title>`s — now reads UI copy from a catalogue rather than a hardcoded literal; see I18N.md's "What's actually extracted." This closes out Milestone 2's phased work. **Mobile client readiness (MOBILE_CLIENT.md) is deliberately left out of any milestone** — not being built soon; it stays designed-not-built with no phase number until a mobile app is actually started.

**Milestone 3 (MILESTONE_3.md), Phases 19–25, is built** — contribution becomes earned and gated rather than optimistic-wiki-anyone-can-confirm. An append-only `ContributionEvent` ledger drives a `guideLevel` cache on the now-universal `GuideProfile` (one row per user, auto-created at first login; `isListed` keeps the pre-existing public `/guides` directory scoped to users who opted into professional listing). Edits to existing adventure pages/trails/spots no longer touch the live row directly — they land as a `PENDING` revision (reusing `PageRevision`/`TrailRevision`/`SpotRevision` from Phase 15 as the queue itself, with new `approvalStatus`/`approvedRevisionId` columns) until enough `guideLevel ≥ 10` votes, or one admin/moderator vote, resolve it; the live row always shows the last *approved* revision, with an "N unapproved changes" control surfacing pending work rather than hiding it. `verificationStatus` is now derived from approval instead of the standalone confirm-button/threshold mechanism this file's "Content trust model" bullet used to describe for trails/spots/pages — that mechanism (`CONFIRMATION_THRESHOLD`, the per-service `confirm()` endpoints) is retired; see MILESTONE_3.md §5.4. A `ContentReport` queue lets any member flag content; a level-10+ reviewer, moderator, or admin resolves it, and an upheld report reverts to the previous approved revision via a new `revertToPreviousApproved()` on each content service (not a call into GEODATA_HISTORY.md's `revert()`, which only files another pending revision) and deducts points from the offending editor. `Role` gains `MODERATOR`, reached only through a `ModeratorApplication` an admin decides — moderators get admin-site login with a documented restricted resource set (no master data, no role/user-status edits, no system settings, no licence-gate override). Runtime-tunable economy values (`approval.threshold`, `approval.minGuideLevel`, per-reason point amounts) live in a new `SystemSetting` table read through a cached `SettingsService`, not hardcoded constants. Phase 25 closed the milestone out: the three notification types deferred from Phases 23–24's pulled-forward set (`CHANGE_APPROVED`, `CHANGE_REJECTED`, `LEVEL_UP`) are wired into the three content services' approve/reject paths and `ContributionsService.applyDelta`; a `recompute:contributions` script (`apps/api/prisma/scripts/recompute-contributions.ts`) re-derives the points/level cache from the ledger for drift correction, alongside the `ContributionsService.recompute()`/`recomputeAll()` methods it wraps; and a pre-existing i18n gap in `NotificationBell.tsx` (the one component I18N.md's Phase 18 sweep had missed, predating Milestone 3) was closed alongside the Milestone-3 UI, which was already fully catalogued through Phases 19–24. See MILESTONE_3.md §12 for what's still explicitly open (reject-threshold auto-expiry, per-image vs. per-page media-approval batching, and others) — none of it blocks the milestone being done.

The markdown docs remain the source of truth for *why* things are shaped the way they are — read them before touching code that contradicts a documented decision. When asked to "implement" or "start building" something new, treat the docs as the spec and extend them (per the conventions below) rather than inventing structure that contradicts what's already decided.

## Reading order / doc map

1. **IDEA.md** — product vision. A non-commercial "OpenStreetMap + Wikipedia + Strava, for adventure in Nepal": map layer, wiki-style article layer, Strava-style activity/social layer, unified under one contributor account. Defines the trust model (unverified → verified via peer confirmation) and the real legal constraint that restricted-region trekking (Annapurna, Manaslu, Upper Mustang) requires a licensed agency.

## Locked architecture decisions (don't relitigate without reason)

- **Three apps, one repo, npm workspaces** (no Nx/Turborepo): `apps/api` (NestJS), `apps/admin` (React + Vite + Refine + Ant Design), `apps/public` (TanStack Start, SSR/file-based routing, chosen over Next.js for SEO with the explicit tradeoff of a smaller ecosystem).
- **Full container dev**: everything — db, api, admin, public — runs via `docker-compose`, all three app services sharing one root `Dockerfile.dev`; nothing needs installing on the host except Docker. Code is bind-mounted with anonymous volumes over each `node_modules` so host installs don't clobber container-native deps.
- **Postgres + PostGIS from day one**, even before any geometry columns exist, specifically so Phase 7 (map layer) needs no extension migration. PostGIS `geometry` columns are `Unsupported(...)` in Prisma — hand-add GiST indexes to migrations, use `$queryRaw`/`$executeRaw` for spatial queries.
- **Prisma** ORM, UUIDv4 string IDs everywhere, `createdAt`/`updatedAt` on every table, models `@@map`'d to snake_case plural table names (columns stay camelCase, unmapped).
- **Soft delete convention**: any table the generic CRUD "delete" route can touch has `isActive Boolean @default(true)`; delete = `isActive = false`, never a SQL `DELETE`. Hierarchical/lookup FKs use `onDelete: Restrict`; content owned exclusively by a parent row uses `onDelete: Cascade` (e.g. `Profile`→`User`, `PageRevision`→`AdventurePage`).
- **Auth is Google OAuth only** — no local email/password, no password hashing. Access JWT (15 min) + refresh token (opaque, hashed in DB, httpOnly cookie, 7 day). Admin bootstrap is an `ADMIN_EMAILS` allowlist checked only on first-login user creation, never on update. Two frontends (`admin`, `public`) can each trigger login, so redirect targets go through a validated `redirectUrl` + `ALLOWED_REDIRECT_URLS` allowlist (open-redirect prevention), round-tripped via the OAuth `state` param.
- **RBAC is minimal**: `Role` enum is just `ADMIN`/`USER`. The richer unverified/verified/moderator *content* trust tiers from IDEA.md are a separate axis modeled per content type (`PageVerificationStatus`, `GeoVerificationStatus`, `GuideVerificationStatus`), not folded into `Role`.
- **Generic CRUD factory** (`common/crud/base-crud.service.ts` + `.controller.ts`) parameterized over a Prisma delegate — used by all master-data tables (flat and hierarchical). Content tables (adventure pages, trails/spots, trip reports) are explicitly **not** generic CRUD — they're compound/transactional operations (e.g. creating a page always creates its first revision in the same transaction).
- **Content trust model varies deliberately by type** — this is a recurring, intentional asymmetry, not inconsistency:
  - Adventure pages: full revision history (`PageRevision`, full-content snapshots, never diffs). **Since Milestone 3 Phase 21**, an edit no longer touches the live row at all — it lands as a `PENDING` revision, and `verificationStatus` is *derived* from whether the approved revision is the latest one, not from a standalone confirmation-count threshold (`CONFIRMATION_THRESHOLD` and the old per-service `confirm()` endpoints are retired). Confirmations survive as `PageConfirmation`, now the approval *vote*, still scoped to a specific revision so stale trust can't ride along after an edit.
  - Trails/spots: **full revision history since Milestone 2 Phase 15** (`TrailRevision`/`SpotRevision`, mirroring `PageRevision`), and the same Milestone 3 Phase 21 approval-gating applies — edits sit `PENDING` until a vote resolves them, at which point `applyApproval()` writes the snapshot to the live row (including PostGIS geometry via `$executeRaw`) and `verificationStatus` is derived the same way as adventure pages. See GEODATA_HISTORY.md for the revision model itself and MILESTONE_3.md §5 for the approval pipeline built on top of it.
  - Trip reports: **no verification tier at all, and never approval-gated** — a trip report is a personal account, not a factual claim; kudos/comments are the only signal. `STORY_CREATE` points post immediately on publish (MILESTONE_3.md §3.2), unlike page/geo edits which only pay out on approval.
  - Guide profiles: verification is **manual-review-only**, never peer-confirmed — credential trust, not content trust. Restricted-district guides must pass through `PENDING_LICENSE_REVIEW`, untouched by Milestone 3's contributor-level axis. `GuideProfile` itself is now universal (one row per user, auto-created at first login) rather than professional-guide-only — see the Milestone 3 status paragraph above.
- **Location hierarchy is real Nepal admin geography** (`Country → Province → District → Municipality`, ~838 rows), not a flat "region" list — populated via a one-off import script, not the no-seed-script convention that applies elsewhere.
- **`apps/public` styling is Tailwind CSS v4** + a small reusable component library (`apps/public/src/components/`) — an earthy pine-green/terracotta palette on warm stone neutrals, dark mode via `prefers-color-scheme` (no manual toggle). `apps/admin` gets the same palette via Ant Design's `ConfigProvider` theme tokens rather than a Tailwind rewrite — the Refine/AntD stack stays, only reskinned.
- **Map rendering is Leaflet + OpenStreetMap tiles** (free, no API key — matches IDEA.md's non-commercial framing), in both `apps/public` and `apps/admin`. Leaflet isn't SSR-safe, so in `apps/public` it's lazy-loaded behind TanStack Router's `ClientOnly` (see `LazyAdventureMap`/`LazyDrawMap`) — never imported at module scope in a file that renders during SSR. **Offline caveat (MOBILE_CLIENT.md, designed not built)**: a future mobile client's offline basemap needs vector tiles (self-hosted PMTiles built from a Nepal OSM extract, served via Caddy directly — never through the OSM tile CDN, whose usage policy forbids bulk downloading), which Leaflet can't render — MapLibre is scoped for mobile only, web stays on Leaflet + raster tiles unchanged. Still no API key, still no vendor; a rendering-library addition, not a reversal of this decision.
- **Admin resources beyond master data are read + moderate, not full authoring** — Adventure Pages, Trip Reports, Trip Groups, Trails/Spots, Guide Profiles all get admin list/show + verification-status/delete actions, but creating/editing the actual content stays in the public contribute flow. This keeps compound-write logic (revisions, confirmations, transactions) in one place instead of duplicating it in admin.
- **`searchVector`/notification-triggering side effects are trigger- and service-layer-maintained, never client-driven** — the same "don't trust the client to keep derived state honest" instinct as `verificationStatus` resets. Postgres triggers keep `AdventurePage.searchVector` in sync with title/summary/latest-revision-content; `NotificationsService` fires from the service layer at the exact point a threshold/event actually happens, not from a controller or the frontend. See FEATURE.md §9.
- **Deployment is one VPS + docker-compose + Caddy, not a managed platform (Vercel/Render/Fly) or Kubernetes** — matches the project's existing all-docker-compose philosophy rather than introducing a new hosting paradigm. `Dockerfile.prod` compiles all three apps; Caddy is the only internet-facing service and gets automatic HTTPS for free from having real domains configured. GitHub Actions (`.github/workflows/deploy.yml`) SSHes in and rebuilds on every push to `main`. See FEATURE.md §10. Notably, `apps/public`'s TanStack Start build only emits a Web-standard fetch handler, not a Node listener or static-file server — `apps/public/server.prod.mjs` is a small hand-written adapter for that gap, not an upstream-provided piece.

## Conventions to carry forward when adding new design docs or schema

- Every new doc should state what it depends on and what it explicitly defers, the way the existing docs cross-reference each other.
- Schema additions for a not-yet-built phase list "required additions to existing models" (reverse-relation fields) separately, and note they're intentionally *not* retroactively applied until that phase is actually implemented — keeps FEATURE.md §2's "Phase 1–5" scope honest.
- Prefer one duplicated-but-simple table over a shared/polymorphic one when Prisma can't express the polymorphism cleanly (e.g. `Media` vs. `TripReportMedia`, or three separate `*Confirmation` tables instead of one generic one).
- Flag open decisions explicitly (a numbered "Open decisions" section) rather than silently picking an answer when something is genuinely undecided.
