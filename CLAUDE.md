# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) and to human developers working in this repository. It is the single technical reference for the project — architecture, schema, conventions, and known gaps. For a non-technical description of the product itself, see [`docs/index.md`](docs/index.md).

## What this repo is

A **working monorepo**, not design docs — `apps/api` (NestJS), `apps/admin` (React + Vite + Refine + Ant Design), and `apps/public` (TanStack Start) are all implemented and run together via `docker-compose up`. Postgres/PostGIS is the only other service. There's a real deployment pipeline (GitHub Actions + docker-compose + Caddy on one VPS), not just local dev.

`apps/api/prisma/schema.prisma` is the single source of truth for the database schema — there is no separate ER diagram to keep in sync with it.

The product has grown in three broad rounds:

1. **Core platform** — auth, master data, adventure pages (wiki-style articles with full revision history), the map/geodata layer (trails/spots), trip reports, guide directory, trip-companion groups, full-text search, in-app notifications, and the deployment pipeline itself.
2. **Depth passes** — geodata changeset history (revision-scoped confirmations, diff/revert), GPX/KML/KMZ/GeoJSON import feeding trail elevation profiles and personal `ActivityTrack`s, spatially-derived district tagging (PostGIS `ST_Intersects`/`ST_Contains`), and UI i18n scaffolding (English-only today, but every string routed through a catalogue).
3. **Contribution economy** — the shift from an optimistic wiki (edits go live immediately) to earned, gated contribution: a points/level ledger, an approval pipeline for page/trail/spot edits, content reporting and moderation, and a `MODERATOR` role reached by application.

Since then, two freestanding community features (Clubs and Club Threads) and a full SEO pass on the public site have shipped, plus a visual identity refresh (glassmorphism surface treatment) on `apps/public`. All of this is described below.

**When asked to "implement" or "start building" something new**: read this file's conventions and locked decisions first, and extend them rather than inventing structure that contradicts what's already decided. Flag genuinely new/undecided questions explicitly rather than silently picking an answer.

## Locked architecture decisions (don't relitigate without reason)

- **Three apps, one repo, npm workspaces** (no Nx/Turborepo): `apps/api` (NestJS), `apps/admin` (React + Vite + Refine + Ant Design), `apps/public` (TanStack Start, SSR/file-based routing, chosen over Next.js for SEO — see "SEO" below for what that promise actually cashed out to).
- **Full container dev**: everything — db, api, admin, public — runs via `docker-compose`, all three app services sharing one root `Dockerfile.dev`; nothing needs installing on the host except Docker. Code is bind-mounted with anonymous volumes over each `node_modules` so host installs don't clobber container-native deps. **`apps/mobile` is a planned exception** (see "Mobile" below): React Native can't be containerized meaningfully — the iOS Simulator needs a macOS host with Xcode, the Android emulator needs host virtualization, and Metro serves physical devices over the LAN — so it runs on the host and talks to the still-containerized API over a LAN IP.
- **Postgres + PostGIS from day one**, even before geometry columns existed, so the map layer needed no extension migration later. PostGIS `geometry`/`tsvector` columns are `Unsupported(...)` in Prisma — hand-add GiST/GIN indexes to migrations, use `$queryRaw`/`$executeRaw` for spatial queries. Watch for spurious auto-generated `DROP INDEX` statements when Prisma regenerates a migration touching an unrelated table — this has bitten the repo repeatedly, and `prisma migrate dev` has consistently refused to run non-interactively inside the container, so the working pattern is `prisma migrate diff` + hand-stripped SQL + `prisma migrate deploy`.
- **Prisma ORM**, UUIDv4 string IDs everywhere, `createdAt`/`updatedAt` on every table except immutable revision/log rows (`createdAt` only), models `@@map`'d to snake_case plural table names (columns stay camelCase, unmapped).
- **Soft delete convention**: any table the generic CRUD "delete" route can touch has `isActive Boolean @default(true)`; delete = `isActive = false`, never a SQL `DELETE`. Hierarchical/lookup FKs use `onDelete: Restrict`; content owned exclusively by a parent row uses `onDelete: Cascade`. A row whose parent shouldn't take it down (a personal record hanging off content that might get deleted) uses `onDelete: SetNull` instead.
- **Auth is Google OAuth only today, Apple sign-in is planned** — no local email/password, no password hashing, ever. Google-only was a locked decision until the mobile plan forced it open: App Store Guideline 4.8 requires an equivalent privacy-preserving login option whenever third-party social login is the primary auth, and Google Sign-In doesn't meet the exemption criteria (no email masking). Sign in with Apple is therefore mandatory for the iOS app and is not optional scope. The migration path (see `MOBILE_PLAN.md`) replaces `User.googleId` with an `AuthIdentity` table keyed `@@unique([provider, providerId])`, so one user can hold both providers; accounts auto-link only on a **provider-verified** email (linking on an unverified one is an account-takeover vector), with a manual link flow for Apple private-relay addresses. Access JWT (15 min) + refresh token (opaque, hashed in DB, httpOnly cookie, 7 day). Admin bootstrap is an `ADMIN_EMAILS` allowlist checked only on first-login user creation, never on update. Two frontends (`admin`, `public`) can each trigger login, so redirect targets go through a validated `redirectUrl` + `ALLOWED_REDIRECT_URLS` allowlist (open-redirect prevention), round-tripped via the OAuth `state` param.
- **RBAC**: `Role` enum is `ADMIN | MODERATOR | USER` (`MODERATOR` added later — see "Contribution economy" below). The richer unverified/verified content-trust tiers are a separate axis modeled per content type (`PageVerificationStatus`, `GeoVerificationStatus`, `GuideVerificationStatus`), not folded into `Role`.
- **Generic CRUD factory** (`common/crud/base-crud.service.ts` + `.controller.ts`) parameterized over a Prisma delegate — used by flat/hierarchical master-data tables. Content tables (adventure pages, trails/spots, trip reports, clubs, threads) are explicitly **not** generic CRUD — they're compound/transactional operations.
- **Content trust model varies deliberately by type** — a recurring, intentional asymmetry, not inconsistency. See "Content trust & the approval pipeline" below for the full picture.
- **Location hierarchy is real Nepal admin geography** (`Country → Province → District → Municipality`, ~838 rows, sourced from the `nepal-places` npm package — not an official government dataset, flagged as a real gap), populated via a one-off import script — the one deliberate exception to "no seed scripts."
- **`apps/public` styling is Tailwind CSS v4** + a reusable component library (`apps/public/src/components/`) — pine-green/terracotta palette on warm stone neutrals, dark mode via `prefers-color-scheme` (no manual toggle). `apps/admin` gets the same palette via Ant Design's `ConfigProvider` theme tokens rather than a Tailwind rewrite. See "Design system" below for the glassmorphism layer added on top.
- **Map rendering is Leaflet + OpenStreetMap tiles** (free, no API key, non-commercial framing), in both apps. Leaflet isn't SSR-safe, so in `apps/public` it's lazy-loaded behind TanStack Router's `ClientOnly` — never imported at module scope in a file that renders during SSR.
- **Admin resources beyond master data are read + moderate, not full authoring** — Adventure Pages, Trip Reports, Trip Groups, Trails/Spots, Guide Profiles, Clubs, Threads all get admin list/show + verification/moderation actions, but creating/editing the actual content stays in the public contribute flow. This keeps compound-write logic in one place instead of duplicating it in admin.
- **Derived state is trigger- and service-layer-maintained, never client-driven** — the same instinct behind `verificationStatus` resets. Postgres triggers keep `AdventurePage.searchVector` in sync; `NotificationsService` fires from the service layer at the exact point a threshold/event happens, never from a controller or the frontend.
- **Deployment is one VPS + docker-compose + Caddy**, not a managed platform or Kubernetes. `Dockerfile.prod` compiles all three apps; Caddy is the only internet-facing service and gets automatic HTTPS from real domains. `apps/public`'s TanStack Start build only emits a Web-standard fetch handler, not a Node listener — `apps/public/server.prod.mjs` is a hand-written adapter for that gap. GitHub Actions (`.github/workflows/deploy.yml`) SSHes in on every push to `main`, runs **`git reset --hard` to `origin/main`** (never `git pull`), and rebuilds via compose — nothing should be hand-edited on the server except `.env`.

## Conventions to carry forward

- Prefer one duplicated-but-simple table over a shared/polymorphic one when Prisma can't express the polymorphism cleanly (e.g. `Media` vs. `TripReportMedia`, or `ThreadReply` mirroring `Comment` rather than a nullable `threadId` bolted onto it).
- A join/attachment relationship that's small and fixed (at most one of each of N types) is expressed as N independent nullable FKs, not a polymorphic `{type, id}` join table — see `Thread`'s four attachment columns.
- A "join request" that's really just an early lifecycle state of the same relationship (e.g. a pending club membership) is one row with a status enum, not a separate request table — collapse it unless the two things are genuinely distinct entities (contrast: `ModeratorApplication`, which really is distinct from `User.role`).
- Flag open decisions explicitly rather than silently picking an answer when something is genuinely undecided — see "Open decisions and known gaps" at the end of this file.

## Architecture notes

**NestJS module map** (`apps/api/src/`): `config/` (Zod-validated env), `prisma/` (global module), `auth/`, `users/` (auth-only fields: id/email/googleId/role/isActive), `profiles/` (name/avatarUrl), `common/crud/` (generic CRUD factory), `master-data/<type>/`, `adventure-pages/`, `geodata/` (trails/spots), `trip-reports/`, `guide-profiles/`, `trip-groups/`, `clubs/`, `threads/`, `tracks/` (activity tracks + GPX/KML/KMZ/GeoJSON parsers), `contributions/`, `approvals/`, `reports/`, `moderator-applications/`, `settings/`, `notifications/`, `uploads/`, `health/`. `JwtAuthGuard` is registered globally via `APP_GUARD` — every route requires a valid token unless `@Public()`-marked (opt out of auth, not in).

**Google OAuth login flow**: browser hits `GET /auth/google?redirectUrl=...` (validated against `ALLOWED_REDIRECT_URLS`, round-tripped via `state`) → Google consent → `GET /auth/google/callback` → `AuthService` upserts `User` (role from `ADMIN_EMAILS`, create-branch only) + `Profile` → issues access (15 min) + refresh (opaque, hashed, httpOnly cookie, 7 day) tokens → 302-redirects to `${redirectUrl}/auth/callback#access_token=...` (fragment, never sent to a server) → frontend reads the fragment, stores the access token in memory only, strips it from the URL. `POST /auth/refresh` reads the cookie, rotates the pair; `POST /auth/logout` clears it. Access tokens aren't individually revocable (stateless JWT tradeoff at 15 min TTL).

**Generic CRUD internals**: `base-crud.service.ts` is a class parameterized over a Prisma delegate providing list/get/create/update/delete — delete is always soft, `list()` filters `isActive = true` by default (`?includeInactive=true`, admin-only, surfaces soft-deleted rows), restore reuses `update(id, { isActive: true })`. `base-crud.controller.ts` is a factory producing a Nest controller with the five REST routes, write routes `@Roles('ADMIN')`.

**API conventions**: prefix `/api/v1/...`; list endpoints return `{ data, total, page, pageSize }`; single-resource endpoints return the resource directly; global exception filter; `class-validator`/`class-transformer` with `ValidationPipe({ whitelist: true, forbidNonWhitelisted: true })` — unknown body fields are rejected.

**Env vars**: `DATABASE_URL` (host `db`, the compose service name), `JWT_ACCESS_SECRET`/`TTL` (15m), `JWT_REFRESH_SECRET`/`TTL` (7d), `GOOGLE_CLIENT_ID`/`SECRET`/`CALLBACK_URL`, `ADMIN_EMAILS`, `ALLOWED_REDIRECT_URLS`, `PORT`. Validated at boot via Zod — fails fast on a missing required var.

## Database schema — models by content layer

Global conventions: UUIDv4 string ids, `createdAt`/`updatedAt` on every table except immutable revision/log tables, snake_case-plural `@@map`, soft delete via `isActive`, `Unsupported(...)` for PostGIS/tsvector columns, `Restrict` for hierarchical/lookup FKs vs. `Cascade`/`SetNull` for parent-owned/parent-independent content.

### Core auth/master data

- **User** — email, googleId (unique), role, isActive. Has one `Profile`, many `RefreshToken`.
- **Profile** — 1:1 with User (Cascade), name, avatarUrl.
- **ActivityType** — self-referencing via `parentId` (unbounded nesting, e.g. Trekking → Teahouse Trekking); cycle prevention is service-layer only.
- **DifficultyLevel**, **Season**, **SpotType**, **Language**, **Tag** — flat master data sharing the generic CRUD service/controller.
- **Country → Province → District → Municipality** — real Nepal admin geography. `District.requiresRegisteredAgency` flags restricted-permit districts (currently just Manang/Mustang/Gorkha — a simplification vs. the real Nepal Tourism Board list). `District.boundary Unsupported("geometry(MultiPolygon, 4326)")?` (nullable — imported polygons for 77 districts, used for spatial district-tagging derivation, see below).
- Migrations auto-run on API container startup (`prisma migrate deploy`). Seed scripts are manual, never wired into startup.

### Adventure pages — wiki/article layer

- **AdventurePage** — title, slug (unique), summary, activityTypeId, difficultyLevelId, durationMin/MaxDays, maxAltitudeMeters, `verificationStatus`, `approvedRevisionId` (nullable unique — the published version), `pendingRevisionCount` (cache), isActive.
- **PageRevision** — full-content Markdown snapshot per edit (never a diff — same shape as Wikipedia's own DB), editSummary, `isSafetyCriticalEdit`, editorId, `approvalStatus` (`PENDING|APPROVED|REJECTED`), `resolvedAt`/`resolvedById`/`rejectionReason`. `@@unique([adventurePageId, version])`.
- **PageConfirmation** — the approval *vote*. Scoped to a specific `revisionId` (not the page), `decision: APPROVE|REJECT`, `@@unique([revisionId, userId])` prevents double-voting.
- **AdventurePageDistrict** — many-to-many, `source: MANUAL|DERIVED` (see district tagging below).
- **AdventurePageSeason**, **AdventurePageTag** — plain many-to-many joins.
- **Media** — url/caption/altText/sortOrder, uploadedById, `approvalStatus`/`resolvedAt`/`resolvedById`/`isActive`. Uploads go through `POST /uploads/images` (local disk, not S3).
- **AdventurePageLike** — deliberately not revision-scoped, never reset on edit (casual appreciation, not a trust claim).
- **AdventurePageVisit** — a "Been Here" marker, deduped per user, timestamped for a future trending query (write path + button exist; the query itself doesn't yet).
- **RelatedAdventurePage** — symmetric self-join; no moderation queue (a named spam-vector risk, not yet a problem).

Write path (all content types with an approval pipeline follow this same shape — see "Content trust & the approval pipeline" below): create writes the live row + a PENDING v1 revision; edit writes only a new PENDING revision, live row untouched until approval.

### Map / geodata layer

- **Trail** — adventurePageId (Cascade, exclusive to one page), name (nullable), `geometry Unsupported("geometry(LineString, 4326)")`, distanceMeters (cached), `source: DRAWN|GPX_IMPORT|RECORDED_ACTIVITY`, verificationStatus, `approvedRevisionId`, `pendingRevisionCount`, optional `elevationProfile` relation.
- **Spot** — same page-exclusivity, spotTypeId, name, description, `geometry Unsupported("geometry(Point, 4326)")`, elevationMeters, same approval fields.
- **TrailRevision**/**SpotRevision** — mirror `PageRevision`: full snapshot per edit including geometry (own GiST index), editSummary, `isSafetyCriticalEdit` (a real stored column here), editorId, `@@unique([trail/spotId, version])`. No `updatedAt` (immutable rows).
- **TrailConfirmation**/**SpotConfirmation** — revision-scoped votes, same shape as `PageConfirmation`.
- GiST indexes on geometry columns are hand-added to migration SQL; SRID 4326 (WGS84) matches any tile provider/GPX source.
- `GET /trails/bbox`/`/spots/bbox` are bounded: `BboxQueryDto` validates and coerces the bbox params (previously raw `@Query()` strings run through `Number(...)`, so `NaN` flowed straight into the SQL), both services `LIMIT 500`, and trails additionally get zoom-adaptive `ST_SimplifyPreserveTopology` at `0.5 / 2^zoom` degrees. Spots are points, so `LIMIT` alone applies.
- **Known gap**: the only spatial predicates in the repo are `ST_Intersects`/`ST_Contains` — a proximity query (`ST_DWithin`, for "nearest lodge"/off-trail detection) doesn't exist yet.

**Spatially-derived district tagging**: fires service-layer, inside the same transaction as trail/spot create or geometry-changing update (never client-driven) — `ST_Intersects` for trails, `ST_Contains` for spots, `INSERT ... ON CONFLICT DO NOTHING` into `AdventurePageDistrict` with `source: DERIVED`. **MANUAL always wins** — derivation is additive-only, never deletes/downgrades a MANUAL row; a manual pick on an existing DERIVED row upgrades it in place (upsert) instead of colliding. Boundary data was imported from the `nepal-geojson` npm package (not OSM/HDX directly), unioned+simplified into one ~410KB fixture. Not backfilled across pre-existing pages — only fires going forward.

**Trail elevation profiles**: `TrailElevationProfile` — a 1:1 sidecar table (`trailId` unique, Cascade), `samples Json` (`[{d, e}, ...]`, whole-object read, never queried into), sampleCount, ascent/descentMeters, min/maxElevationMeters. Chosen over `LineStringZ` geometry because `Trail.geometry`'s typmod forbids Z and a chart needs distance/elevation pairs, not raw vertices. **The invalidation rule**: editing a trail's geometry deletes its elevation profile in the same transaction as confirmation invalidation (a stale profile is the same class of lie as a stale confirmation) — but this must be geometry-conditional, not unconditional; renaming a trail must not destroy its profile.

**GPX/KML/KMZ/GeoJSON import** (`apps/api/src/tracks/parsers/`): parsed server-side only (never trust client-derived geometry/aggregates), via `fast-xml-parser` + a hand-written mapper. Guardrails: max file size, max-vertex cap with simplification, reject files with no track points, reject out-of-Nepal bboxes. **Privacy**: `<time>` elements are discarded on import for anything that becomes public `Trail` geometry — a raw GPX timestamp reveals exactly when someone was at a coordinate on a public, anonymous site.

**ActivityTrack** — the Strava-analogue geometry a `TripReport` never had natively. userId (Cascade — personal data), optional adventurePageId/tripReportId (SetNull — a personal record must outlive linked public content), `geometry` (simplified path) + `samples Json` (full-fidelity, **keeps timestamps** — privacy-stripping is destination-scoped, not parser-scoped: a private ActivityTrack keeps time data, a public Trail strips it), `source: RECORDED|IMPORTED`, `visibility: PRIVATE|PUBLIC` (default PRIVATE), `privacyTrimMeters` (trims served geometry ends for non-owners), `clientUuid` (idempotency key for upload retries). `POST /activity-tracks/:id/promote-to-trail` and `POST /activity-tracks/:id/propose-trail-update` let a personal recording contribute back to the public map. A `TripReport` can attach the author's own `ActivityTrack`s at create/edit time (`activityTrackIds`).

### Trip reports — social layer

Deliberate asymmetry: **no verification tier at all, never approval-gated** — a trip report is a personal account, not a factual claim; kudos/comments are the only signal, and its points post immediately on publish rather than only on approval.

- **TripReport** — adventurePageId (Cascade), authorId (Restrict), title/description, `dateCompleted` (separate from `createdAt`), durationDays, actualCostAmount, `currency` (fixed short list, validated in DTO), optional `clubId` (SetNull — a report can outlive a deactivated club), `activityTracks` relation.
- **TripReportMedia** — its own table (not shared `Media`).
- **TripReportKudos** — `@@unique([tripReportId, userId])` stops self-inflation.
- **Comment** — self-referencing `parentCommentId` (Cascade — deleting a comment takes replies with it); reply tree built in application code from a flat fetch.

### Guide directory

A third, separate trust model: `GuideVerificationStatus` (`UNVERIFIED|PENDING_LICENSE_REVIEW|VERIFIED`) promotes **only via manual moderator review**, never peer-confirmation — credential trust, not content trust.

- **GuideProfile** — universal, one row per user, auto-created at first login. licenseNumber, bio, rateMin/Max/rateUnit (informational only), `currency`, verificationStatus, `isListed` (opt-in to the public `/guides` directory), plus contribution-economy caches: `contributionPoints`, `guideLevel`, `approvalsGiven`.
- **GuideSpecialty**/**GuideRegion**/**GuideLanguage** — many-to-many joins.
- Restricted-region enforcement: if any `GuideRegion` references a `District.requiresRegisteredAgency` district, that guide can only reach `VERIFIED` via `PENDING_LICENSE_REVIEW` — never a shortcut.

### Trip-companion groups

Deliberately **no messaging model** (chat is scope creep beyond an informational-only stance).

- **TripGroup** — adventurePageId (Cascade), title, description, dateStart/dateEnd, createdById.
- **TripGroupMember** — `role: ORGANIZER|MEMBER`, `@@unique([tripGroupId, userId])`.
- Known gaps: no group-size cap, no join-approval/private mode, no organizer reassignment on leave.

### Clubs — freestanding community

A persistent community (e.g. "Kathmandu Hikers Club"), distinct from a page-scoped `TripGroup`. Any logged-in user can create one and becomes its `OWNER`. `PUBLIC` clubs are instant-join; `PRIVATE` clubs are join-by-request. **No `ContributionEvent` points for any club activity.**

- **Club** — name, description, coverImageUrl, `visibility: PUBLIC|PRIVATE`, createdById, isActive.
- **ClubMember** — `role: OWNER|MEMBER`, `status: PENDING|APPROVED|DECLINED`, decidedById/decidedAt. `@@unique([clubId, userId])`.
- **A `PENDING` `ClubMember` row *is* the join request** — no separate request table (see "Conventions" above).
- Club deactivation is a soft delete; `TripReport.clubId`'s `onDelete: SetNull` never actually fires from a soft delete, so a report can stay tagged to an inactive club — consistent with how soft deletes elsewhere don't cascade through other tables' FKs.
- Admin moderation is gated to `ADMIN` + `MODERATOR` (a deliberate divergence from Trip Groups, which only checks `ADMIN`).
- Private-club detail pages return a trimmed shape to non-members (name/description/visibility, no roster) rather than a 404, plus the caller's own `viewerMembership` status so the UI can show "request pending" without leaking the member list.
- Routes: `GET/POST /clubs`, `GET /clubs/admin/all` (`@Roles(ADMIN, MODERATOR)`, static route registered before `:id`), `GET /clubs/mine`, `GET/PATCH/DELETE /clubs/:id`, `POST/DELETE /clubs/:id/members` (join/leave), `POST /clubs/:id/join-requests`, `GET/PATCH /clubs/:id/join-requests(/:id)`.
- Open decision: no `ClubRole` co-owner/admin tier beyond `OWNER`/`MEMBER` yet.

### Threads — a club's discussion feed

A club-native discussion post: Markdown content, one fixed-enum tag (`ThreadTag: DISCUSSION|TRIP_SHARE|QUESTION|ANNOUNCEMENT|RANDOM`), up to one each of four optional attachments (`TripReport`/`Trail`/`Spot`/`AdventurePage`). One level of replies. Threads are the club feed's primary unit.

- **Thread** — clubId (Cascade — a thread belongs to its club), authorId, content, tag, isPinned (moderator-set, separate from the author's own `update()`), four independent nullable attachment FKs (`SetNull` — a thread is a discussion *about* content, not a container for it, so the attached item disappearing must not destroy the thread).
- **ThreadReply** — mirrors `Comment`'s shape (self-referencing `parentReplyId`, one level of nesting) rather than a nullable `threadId` bolted onto `Comment` — see "Conventions" above.
- **No approval-gating, no revision history, no points** — same reasoning that exempts `TripReport`.
- Pin/lock (moderator tier) is a separate endpoint from the author's own edit — different authorization path. Delete is allowed for the author, club owner, club moderator, or site staff, but the **public UI deliberately hides the pin/delete controls for site ADMIN/MODERATOR viewers** who aren't also a club owner/moderator — an admin capability that shouldn't visibly leak into the public site, even though the API itself still allows it (the admin dashboard's own Thread management uses the same endpoints).
- `Thread`/`ThreadReply` are reportable via the same `ContentReport` queue as everything else (see below).
- Reuses `ClubsService.getActingTier` (widened from private to shared) for `STAFF`/`OWNER`/`MODERATOR` tiering, rather than re-deriving it.
- Three minimal `search?q=` endpoints (`GET /trip-reports/search`, `/trails/search`, `/spots/search`) exist only to back the attachment picker — not a general search service.

### Search & notifications

- **Full-text search**: Postgres `tsvector`/GIN, no separate search service. `AdventurePage.searchVector` is trigger-maintained (never written by app code) from title + summary + latest revision content. `GET /adventure-pages/search?q=` ranks via `ts_rank`. Covers adventure pages only — trip reports, trails/spots, guide profiles aren't indexed.
- **Notification** — one-way system messages (not chat): userId, `type`, `message` (precomputed string, not template+params — simpler, at the cost of not being retroactively re-localizable), linkUrl, isRead. Bell icon polls every 60s, no sockets. Self-notifications suppressed at the service layer.

### Deployment

One VPS, five containers via `docker-compose.prod.yml`: Caddy (only internet-facing service, auto HTTPS), api (runs `prisma migrate deploy` on every start), admin (Vite SPA via nginx), public (TanStack Start SSR via `server.prod.mjs`), db (no host-published port). GitHub Actions deploy workflow SSHes in on every push to `main` and rebuilds via compose. No zero-downtime rollout (accepted at current traffic).

## Content trust & the approval pipeline

**Conceptual shift, already fully built**: from an optimistic wiki (edits go live immediately, confirmations are just a trust badge) to earned and gated contribution.

- **Points/levels**: an append-only `ContributionEvent` ledger (userId, reason, signed points, targetType, targetId with no FK — a deliberate exception to the "avoid polymorphic tables" convention, since this is an audit log never joined for referential integrity) drives a `guideLevel` cache on `GuideProfile`. Points post **only on approval** (except `STORY_CREATE`, which posts immediately since trip reports are never gated). Self-edits earn nothing. The level curve escalates (`threshold(n) = 10·n·(n−1)`) — level 10 unlocks approval-voting rights (~900 pts), level 25 unlocks moderator-application eligibility (~6,000 pts).
- **Approval pipeline**: the existing revision tables (`PageRevision`/`TrailRevision`/`SpotRevision`) **are** the pending queue, not a parallel store — they carry `approvalStatus`, `resolvedAt/ById`, `rejectionReason`; the parent row carries `approvedRevisionId` (the published version) and `pendingRevisionCount`. Create writes the live row + a PENDING v1 revision immediately (visible with an "Unapproved" badge); edit writes only a new PENDING revision, live row untouched until resolved. Approve applies the snapshot to the live row (including PostGIS geometry via `$executeRaw`), sets `approvedRevisionId`, supersedes other pending revisions of the same target as REJECTED. The `*Confirmation` tables are the votes (`decision: APPROVE|REJECT`).
- **Eligibility**: voting requires `guideLevel >= approval.minGuideLevel` (default 10) or `ADMIN`/`MODERATOR`; never vote on your own revision; resolved at `approval.threshold` (default 5) matching votes, or instantly on a single admin/moderator vote.
- **`verificationStatus` is derived, not confirmation-counted**: no approved revision → UNVERIFIED; approved = latest → VERIFIED; pending safety-critical edit or upheld-report revert → NEEDS_REVIEW. (The older "reset verification + delete all confirmations on edit" rule is retired — confirmations go stale for free by pointing at a superseded revision instead.)
- **`SystemSetting`** — a runtime-tunable key/value table (`approval.threshold`, `approval.minGuideLevel`, `moderator.minGuideLevel`, `reports.maxOpenPerUser`, per-reason point values, plus app-branding keys like `app.name`), cached `SettingsService`, admin-only edit, every write logged. This is why the app's own name/tagline is a config value, not a hardcoded string.
- **`ModeratorApplication`** — requires `guideLevel >= moderator.minGuideLevel`, no existing PENDING application; admin-only review; approval sets `role = MODERATOR` in the same transaction. Moderators get admin-site login but **cannot**: change roles/approve moderator applications, deactivate/reactivate users, edit master data or location hierarchy, edit system settings, override the restricted-district guide licence gate. Everything else (approve/reject revisions, resolve reports, soft-delete, adjust verificationStatus) is allowed. Club/thread moderation additionally allows `MODERATOR` where Trip Groups only allow `ADMIN` (see "Clubs" above).
- **`ContentReport`** — reporterId, targetType/targetId, reason, status. Filed by any member (rate-limited per user), resolved by a level-10+ reviewer/moderator/admin (never the reporter or the content's author). Upheld: media soft-deletes + point penalty; trail/spot/page revision reverts to the previous approved snapshot via `revertToPreviousApproved()` (a direct apply — **not** a call into the revision system's own `revert()`, which would only file another pending revision) + point penalty; trip report/comment/thread/thread-reply soft-delete. Rejected reports carry no penalty.
- **Gated vs. not**: pages/trails/spots (create+edit) are gated; media is gated for points only (visible immediately with a badge); trip reports/comments/kudos/likes/activity tracks/trip groups/clubs/threads/guide-profile-professional-fields are **not** gated.

## Design system

Locked palette stays pine-green (`#2f6b4f` at 600) primary / terracotta (`#c1633c` at 500) accent on Tailwind stone neutrals, `prefers-color-scheme`-driven dark mode, `apps/admin` untouched (AntD `ConfigProvider` theming only) — a later glassmorphism pass added a translucent **surface treatment** on top of this palette, `apps/public` only, not a palette replacement.

- Three glass elevation tiers (`--glass-bg-1/2/3`, tinted from the brand palette, defined in `apps/public/src/styles.css`) plus shared border/highlight/shadow tokens, with `@supports not (backdrop-filter)` and `prefers-reduced-transparency`/`prefers-contrast: more` fallbacks to a solid surface built in from the start, not bolted on later.
- Applied to: the sticky header (now two independent floating pills — logo left, nav+auth right — rather than one continuous bar, so the background mesh shows through the gap), card grids (`Card`'s opt-in `glass` prop), modals/dropdowns (notification bell, account menu), map overlay buttons (fullscreen/locate toggles), and the landing search bar. Deliberately left solid: the photo lightbox (a scrim should isolate the image, not let brand color bleed through), and non-card panels like forms/login/edit screens.
- A `GradientMesh` component (fixed, full-viewport, behind everything) gives the glass surfaces real color/texture to refract — a single global layer, not per-page, so scrolling never loses it.
- Buttons ended up outline-style with a thicker border and no glow (glow/neon variants were tried and explicitly reverted per direct feedback) — if touching `Button.tsx`, match the current flat-outline convention rather than reintroducing the earlier glow treatment.
- **Trait badges** (Verified, Expert Only, Hidden Gem, Family Friendly, Pet Friendly) render on trail/spot cards. `Verified` reads the entity's own `verificationStatus`; the other four have no Trail/Spot-level schema source, so they're derived from the parent `AdventurePage`'s `difficultyLevel`/`tags` rather than adding new schema.
- **Map-as-hero**: the adventure-page detail route's map is a persistent hero element — desktop gets a bounded split section (quick-facts/trail list left, map right); mobile gets a full-bleed map with a tap-to-toggle peek/expanded sheet. One Leaflet instance shared across both breakpoints via CSS Grid reflow (`MapHeroLayout.tsx`), not two parallel maps.
- Empty-state copy across public content routes uses an exploration voice ("No one has explored this route yet. Be the first explorer.") — moderation/report-queue empty states deliberately stayed neutral/functional, that voice doesn't fit an internal utility screen.
- Explicitly not adopted from any external design-brief review: a Swiss-grid/bento layout system, a wholesale palette or no-dark-mode change.

## SEO (`apps/public` only — `apps/admin` is a crawled-never dashboard, out of scope)

- **`apps/public/src/lib/seo.ts`**'s `buildMeta({ title, description, path, image?, noindex?, jsonLd? })` is the one call every route's `head()` goes through — title/description/OG/Twitter tags, canonical link, and (since `head()` supports a first-class JSON-LD meta entry in the installed TanStack Start version) structured data too. Don't hand-roll a route's meta tags outside this helper.
- Canonical base URL is a build-time `VITE_SITE_URL` (mirrors the existing `VITE_API_URL` pattern — baked in at build, not read at runtime).
- **`robots.txt` is a static file** (`apps/public/public/robots.txt`) — the disallow list changes at the same slow rate as the route tree, so a static file is simpler than keeping a generated one in sync. **`sitemap.xml` is a server route** (`apps/public/src/routes/sitemap[.]xml.ts`) since its content is DB-driven (every adventure page/listed guide/active club slug).
- `noindex, follow` (via `buildMeta`'s flag) covers auth/action routes that are fine to crawl-and-drop but shouldn't be indexed (login, edit/new forms, the moderation queue, user-profile pages, unlisted guides, private clubs, thread detail pages since thread content is ephemeral/user-generated). `robots.txt`'s `Disallow` covers truly private trees wholesale (`/account/`, `/me/`) instead.
- `NotFound`/`ErrorPage` components set real 404/500 HTTP status codes, not a friendly 200 page — verified via `curl -I`, since a soft-404 is a real SEO foot-gun.
- Sitemap indexes only public, crawlable, content-bearing pages — no auth-gated, action-oriented, or per-user routes.

## Open decisions and known gaps (consolidated)

**Database / master data**
- Nepal geography data (`nepal-places` npm package) and `requiresRegisteredAgency`'s district list (Manang/Mustang/Gorkha only) aren't official sources — re-derive from the Ministry of Federal Affairs / Nepal Tourism Board before relying on either anywhere authoritativeness matters.

**Adventure pages / geodata**
- Tags are settable only at page-creation time, not editable afterward.
- Related-page suggestions have no moderation queue (named spam vector, not yet a problem).
- Concurrent-edit version race on revisions (read-then-write, unique-constraint-guarded only) — `SELECT ... FOR UPDATE` is the fix if concurrent editing ever becomes real.
- `verificationStatus` stays denormalized rather than confirmation-count-joined; revision retention is unbounded (no pruning designed).
- `ST_DWithin` (proximity queries) doesn't exist yet.
- District derivation isn't backfilled across pre-existing pages; no `Municipality`-level boundaries; no intersection-length threshold for border-hugging routes.
- Whether `Spot.elevationMeters` should auto-fill from a nearby trail profile, and whether GPX/KML waypoints should become candidate `Spot`s automatically, are both undesigned.

**i18n**
- Only English ships today, though the library/catalogue plumbing is in place for a second locale — which locale ships first, and machine vs. human translation, is the actual open blocker.
- `Notification.message` (precomputed string) and ~46 API exception messages are out of scope for i18n until a second locale is real. Full-text search hardcodes `to_tsvector('english', ...)`.

**Trip groups**
- No group-size cap, no join-approval/private mode, no organizer reassignment on leave.

**Clubs / Threads**
- No `ClubRole` co-owner tier beyond `OWNER`/`MEMBER`.
- No general cross-entity search service — the three `search?q=` endpoints backing the thread attachment picker are a deliberate narrow stopgap, not a precedent to extend elsewhere without reconsidering.

**Search & notifications**
- No notification preferences (can't mute a category), no push/email delivery — in-app bell only.
- Search covers adventure pages only.

**Contribution economy**
- Reject threshold mirrors approve threshold — no auto-expiry for stuck pending items.
- Whether media approval should batch with its parent page revision instead of per-image voting; whether moderators should eventually edit master data.
- Pre-Milestone content is treated as retroactively approved and paid accordingly, even though approval didn't exist when it was made — an accepted backfill-fairness tradeoff.

**SEO**
- Per-entity generated OG images (composited social cards) aren't built — a single static default image plus an entity's own photo where one exists is the current approach.
- `hreflang`/locale-alternate tags don't apply yet (English-only).

**Mobile** (Phases 0–5 done, Phase 3 at reduced scope, Phase 6 onward not started — full plan in [`MOBILE_PLAN.md`](MOBILE_PLAN.md))
- An `apps/mobile` React Native/Expo client is planned and specified: full `apps/public` parity plus offline maps, offline content, background GPS recording, push notifications, and native camera upload. Expo dev builds from day one (Expo Go can't load the native modules involved), NativeWind for styling, and `packages/api-types` as a new shared workspace so mobile isn't a third hand-maintained copy of every API shape.
- **Phase 0 (API prerequisites) and Phase 1 (scaffold + auth) are done.** `apps/mobile` exists, runs on the host (not docker-compose), and has: Expo Router file-based nav, a `metro.config.js` with `disableHierarchicalLookup` + explicit `nodeModulesPaths`/`watchFolders` (apps/public/apps/admin pin different React versions than Expo's exact pin, so Metro must not resolve a hoisted sibling copy), an API client (`src/lib/api.ts`, `src/lib/auth-fetch.ts`) reading `EXPO_PUBLIC_API_URL` from apps/mobile's own `.env` (not the root one — Expo loads env from its own project root), Google native sign-in through `POST /auth/google/mobile` with the refresh token in `expo-secure-store` and the access token in memory (`src/lib/auth/`), NativeWind wired to the same pine-green/terracotta palette via `tailwind.config.js` (`darkMode: 'media'`, OS-driven, no manual toggle — matches the web convention), and Sentry (no-op without `EXPO_PUBLIC_SENTRY_DSN`).
- **Phase 2 (read-only browsing) is done.** `Stack.Protected` gates a `sign-in` screen against a `(tabs)` group (Discover/Guides/Clubs/Account) plus `adventures/[slug]` detail routes that sit outside the tabs (reached only from Discover, so no path collision with the tab list screens). React Query (`src/lib/query-client.ts`, `src/lib/resources/*.ts`) is the data-fetching layer — a new addition, since `apps/public`'s TanStack Start loaders are SSR-specific and don't port. `packages/api-types/src/content.ts` holds the read-only response shapes. **Notable finding from building this phase**: no endpoint joins a display name onto an author/user reference — `TripReport`, `Comment`, `ThreadReply`, and `GuideProfile` all return bare `authorId`/`userId`, resolved client-side via a `UserRef` component (`GET /users/:id/profile`, ported from `apps/public`'s `UserRef.tsx`, React-Query-cached by id). `Comment` and `ThreadReply` are both nested one level server-side (flat-fetched, nested in application code), not flat lists — mirror that shape rather than assuming a flat array. Maps, the `ElevationProfile` chart, and every mutation (like/visit/kudos/join/reply/comment-post) are deferred past Phase 2 — those buttons simply aren't rendered yet, not rendered-disabled.
- **Phase 3 (offline) is done, at reduced scope agreed with the user.** The self-hosted PMTiles archive Phase 3 originally assumed doesn't exist anywhere in this repo (an intent named in this file, not a built asset), so real offline map-pack downloads were deferred rather than blocked on sourcing/building it. What shipped instead: a first-ever map screen (`apps/mobile/src/app/adventures/[slug]/map.tsx`, `src/components/AdventureMap.tsx`) using `@maplibre/maplibre-react-native` v11 against the free, no-API-key [OpenFreeMap](https://openfreemap.org) style — matches this file's own "free, no API key" map ethos — with trail/spot geometry overlaid; and a full local SQLite content mirror (`expo-sqlite`, `src/lib/offline/`) behind a "Download for offline" gesture on the adventure detail screen, with the existing `useAdventurePage`/`useTrails`/`useSpots` hooks (`src/lib/resources/adventure-pages.ts`) extended in place to read cache-first via `@react-native-community/netinfo` connectivity checks — screens didn't change, only the hooks. The tile-serving spike itself is resolved on paper (MapLibre Native's `pmtiles://` protocol doesn't support offline pack caching at all — confirmed via MapLibre's own docs — so the fix is serving plain HTTP `{z}/{x}/{y}.pbf` tiles from apps/api via the `pmtiles` npm package and letting MapLibre's standard `OfflineManager` bbox-download against that instead), it just isn't built yet. Two Metro gotchas from this phase: MapLibre Native has no web target and crashes `expo export --platform web` at module-load (not a graceful runtime no-op) — worked around with a `.web.tsx` platform-split stub; `expo-sqlite`'s web build needs `.wasm` in `metro.config.js`'s `resolver.assetExts` or the same export fails.
- **Phase 4 (GPS recording) is done.** Two-layer adaptive, distance-filtered sampling (`src/lib/recording/sampling.ts`) — `expo-location`'s own `distanceInterval`/`timeInterval` throttle fixes at the OS level, then `shouldKeepFix` applies a second app-level gate whose threshold widens at rest (rejects GPS drift jitter) and near a fast pace (fewer points per meter), narrows at an ordinary walking speed, plus a bounded 120s heartbeat so a stationary recording doesn't look dead — this is what keeps a naive 1Hz GPS trace from draining a phone in ~5 hours. `expo-task-manager` background delivery (`src/lib/recording/location-task.ts`, registered once at `app/_layout.tsx` module scope so a cold OS relaunch can still deliver a batch) reads which session is active from a `recording_meta` SQLite key rather than in-memory state, since a background relaunch gets a fresh JS context. Foreground-permission-only devices degrade to a `watchPositionAsync` subscription that stops when backgrounded — a surfaced degradation, not a silent gap. Recording state (`recording_sessions`/`recording_points` tables in the same SQLite db as Phase 3's offline mirror, see `src/lib/offline/db.ts`) plus a local SQLite outbox (`src/lib/recording/outbox.ts`) syncing via `POST /activity-tracks` with `clientUuid` idempotency and `GET /me/activity-tracks?since=` for tombstone reconciliation — a track deleted on another device gets evicted locally rather than silently re-uploaded. Screens: `app/tracks/{index,new,record}.tsx`, reached from the Account tab. **Per the plan's call to unit-test the one place where the failure mode is silent data loss**: `src/lib/recording/sync-reducer.ts` is a pure state machine (enqueue/upload-start/success/failure/tombstone, exponential backoff capped at 30s, a 5-attempt give-up ceiling) with no SQLite/network imports, fully covered by `sync-reducer.test.ts` (`outbox.ts` wraps it with the real persistence/network calls); `sampling.ts`'s filter is covered too since it was cheap to add. First `jest`/`jest-expo` setup in the mobile app - `npm run test` in `apps/mobile`.
- **Phase 5 (contribute/write flows) is done, full scope** (social mutations, trip-report authoring with camera upload, and full adventure-page/trail/spot create+edit with map-geometry drawing — the user explicitly chose full scope over a narrower slice). `packages/api-types/src/content.ts` gained every Phase 5 request DTO (`CreateAdventurePageRequest`, `CreateTrailRequest`/`CreateSpotRequest` + their `Update*` variants, `SubmitRevisionRequest`, `CreateTripReportRequest`, `CreateCommentRequest`, `CreateThreadRequest`/`CreateThreadReplyRequest`, `CreateClubRequest`, `DecideClubJoinRequestRequest`, `AddMediaRequest`, `UploadImageResponse`, and `PointGeometry`/`LineStringGeometry`), hand-mirrored off the NestJS DTOs — still no codegen. Every new mutation hook (`src/lib/resources/*.ts`) follows the one existing `useDownloadAdventure` template: `useMutation` + `onSettled` → `queryClient.invalidateQueries`. New shared components: `src/lib/upload.ts` (`pickAndUploadImage` — `expo-image-picker` + `expo-image-manipulator` re-encode to JPEG client-side, since `POST /uploads/images` has no HEIC in its whitelist), `FormField.tsx`/`Select.tsx`/`MultiSelectChips.tsx` (RN form primitives — no native `<select>`, so `Select` is a modal list picker), and `DrawMap.tsx` — a hand-rolled tap-to-add-point MapLibre interaction (no drawing library, same as `apps/public`'s Leaflet `DrawMap.tsx`), reusing `AdventureMap.tsx`'s GeoJSON rendering pattern. Geometry stays GeoJSON `[lng, lat]` end-to-end with **no coordinate swap anywhere** — MapLibre's own press event already reports `lngLat` in that order, unlike Leaflet which needed one at the render boundary. `DrawMap.tsx` needed the same `.web.tsx` platform-split stub as `AdventureMap.tsx` (Phase 3's MapLibre-has-no-web-target gotcha applies to every new draw screen too). New screens: social composers (kudos/comment/reply) inlined into the existing trip-report/thread detail screens; club join/leave/request + owner-only join-request review (`clubs/[clubId]/join-requests.tsx`) + thread creation (`clubs/[clubId]/threads/new.tsx`); trip-report creation (`adventures/[slug]/trips/new.tsx`, with an own-`ActivityTrack` attach picker sourced from Phase 4's local `RecordingSession.serverId`); adventure-page create (`adventures/new.tsx`, atomic page+trail+spots submit matching `apps/public`'s transactional shape) and content-only edit (`adventures/[slug]/edit.tsx`, matching `apps/public`'s own content-only scope — metadata fields stay create-only on both clients); trail/spot create+edit (`adventures/[slug]/trails/new.tsx` doubles as the edit flow when a trail already exists, `adventures/[slug]/spots/new.tsx`). Deliberately **not** built this pass: revision-voting UI, the review-queue screen, GPX-import-on-mobile, and moderator-only actions (verification-status PATCH, thread pin/lock) — all flagged as later concerns, not gaps in this pass's own scope.
- Verification so far (all phases) is `tsc`/`expo lint`/`expo export --platform web`/`jest` clean; the real physical-device pass (sign-in/cold-restart/logout, browsing through Discover → adventure → trip report, Guides, Clubs → thread, the map screen + offline download/airplane-mode/eviction flow, a real GPS recording through pause/resume/background/kill-and-relaunch, and now every Phase 5 write flow including camera upload and MapLibre tap-to-draw) still needs to happen on a dev machine with Xcode/Android tooling — background location, camera permissions, and MapLibre press-to-draw in particular can't be verified without a physical device or simulator.
- **Blocking API work before any mobile code** (Phase 0 in the plan, now shipped): a JSON login endpoint (the current flow is entirely browser-redirect-shaped), a body-based refresh variant (currently cookie-only), the missing `secure` flag on the refresh cookie (a real bug worth fixing independently of mobile), rate limiting — which **must** ship together with `app.set('trust proxy', 1)`, since Caddy proxies every request and without it `req.ip` is Caddy's container IP, turning a per-IP limiter into a global lockout — and the `AuthIdentity` migration above.
- **Two sync bugs in `tracks.service.ts` surfaced by the mobile audit, fixed in Phase 0 and now exercised by Phase 4's outbox**: `listSince` filters `isActive = true`, so a track deleted on one device never disappears from another (no tombstones) - fixed via the tombstone shape `outbox.ts`'s `reconcileTombstones` consumes; and it's unpaginated, which is fine for deltas but unbounded on a fresh install where `since` is epoch - fixed via cursor pagination.
- Offline basemaps still need self-hosted vector tiles (PMTiles from a Nepal OSM extract) since Leaflet can't render vector tiles and the OSM tile CDN forbids bulk downloading — MapLibre stays scoped to mobile only, web stays Leaflet+raster. The delivery mechanism is resolved (see the Phase 3 bullet above: a `pmtiles`-package-backed `apps/api` tile route + MapLibre Native's `OfflineManager`), but the archive itself and the tile route don't exist yet — mobile's map screen runs against a free hosted tile source (OpenFreeMap) in the meantime. Downloads will be scoped to a single adventure's buffered bbox (tens of MB), not all of Nepal (300–800MB), once built.
- **Store-mandated work that can't be skipped**: Sign in with Apple (Guideline 4.8, see the auth decision above) and in-app account deletion (Guideline 5.1.1(v)) — there's no delete-account route today, and because `TripReport.authorId` is `Restrict` and revisions carry `editorId`, deletion is soft-delete + anonymize (retain authorship as "[deleted user]", hard-delete `ActivityTrack`s) rather than a cascade that would tear holes in revision history.
- The uploads MIME whitelist omits `image/heic`, so iOS camera uploads fail out of the box; mobile transcodes to JPEG and downscales client-side before upload rather than loosening the server.
