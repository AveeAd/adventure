# Mobile App (`apps/mobile`) — Plan

## Context

The web platform (`apps/api`, `apps/admin`, `apps/public`) is feature-complete per CLAUDE.md's three build rounds. The goal is a React Native mobile app with **full feature parity** with `apps/public`, plus capabilities the web app structurally can't offer: **offline maps and offline content**, **background GPS activity-track recording**, **push notifications**, and **native camera upload**.

A pre-planning audit of the codebase surfaced nineteen gaps, several of them store-mandated blockers that force revisiting locked architectural decisions. All have now been resolved into the decisions below; the audit findings themselves are preserved in "Why these decisions" at the end for future reference.

---

## Locked decisions

| Area | Decision |
|---|---|
| Framework | React Native via Expo, **EAS dev builds from day one** (Expo Go is unusable — background location, MapLibre, and SQLite are all native modules) |
| Location | `apps/mobile` workspace in this monorepo, **running on the host, not in Docker** |
| Auth identity | New **`AuthIdentity` table** (`provider`, `providerId`) replacing `User.googleId` — one user can hold both Google and Apple |
| Account linking | **Auto-link on a matching provider-verified email**; manual "link account" flow in settings for Apple private-relay addresses |
| Account deletion | **Soft-delete + anonymize** — retain revision/report authorship as "[deleted user]", hard-delete `ActivityTrack`s |
| Shared types | New **`packages/api-types`** workspace, hand-written, consumed by all clients |
| Offline content | **Explicit per-adventure download** into local SQLite |
| Offline tiles | **Per-adventure bounding box**, buffered — same gesture as the content download |
| API compatibility | **Min-version check + additive-only policy** on `/api/v1` |
| Styling | **NativeWind** (ports the existing Tailwind palette and dark-mode conventions) |
| Testing | **Sync/offline logic only** (Jest); everything else manual, per repo convention |
| Photo uploads | **Client-side transcode + resize** (`expo-image-manipulator`); server stays strict |
| Sequencing | Schema-affecting and hard-to-retrofit work now; store-compliance surfaces before submission |

Two of these knowingly diverge from CLAUDE.md's locked decisions and should be written back into it: **"Auth is Google OAuth only"** (Apple sign-in is App Store–mandated) and **"full container dev"** (`apps/mobile` cannot run in Docker). A third CLAUDE.md item is simply stale and should be dropped: the "known gap" claiming `/trails/bbox` and `/spots/bbox` lack `LIMIT`/simplification/DTO validation — `BboxQueryDto`, `LIMIT 500`, and zoom-adaptive `ST_SimplifyPreserveTopology` are already implemented.

## Phase 0 — API prerequisites (blocking)

Everything here is additive: the existing cookie-based browser flow must keep working untouched, verified before moving on.

**1. `AuthIdentity` migration.** Introduce the table and backfill from existing users, then drop `User.googleId`:

```prisma
model AuthIdentity {
  id         String       @id @default(uuid())
  userId     String
  user       User         @relation(fields: [userId], references: [id], onDelete: Cascade)
  provider   AuthProvider // GOOGLE | APPLE
  providerId String
  email      String?      // per-provider email; Apple relay differs from User.email
  createdAt  DateTime     @default(now())
  updatedAt  DateTime     @updatedAt

  @@unique([provider, providerId])
  @@index([userId])
}
```

This is a **data-moving migration**: insert one `GOOGLE` row per existing user from their `googleId`, verify counts match, then drop the column. Per CLAUDE.md, `prisma migrate dev` has consistently refused to run non-interactively in the container — use `prisma migrate diff` + hand-stripped SQL + `prisma migrate deploy`, and check the generated SQL for spurious `DROP INDEX` statements on unrelated tables.

`AuthService.handleGoogleLogin` changes from "upsert User by googleId" to "find `AuthIdentity` by `(GOOGLE, sub)` → else find User by verified email and attach a new identity → else create User + identity", all inside the existing transaction that also upserts `Profile` and `GuideProfile`. **Only auto-link when the provider asserts the email is verified** (Google's `email_verified` claim; Apple always verifies) — linking on an unverified email is an account-takeover vector.

**2. JSON mobile login** — `POST /api/v1/auth/google/mobile`. Accepts a Google ID token from the native SDK, verifies it server-side via `google-auth-library`'s `OAuth2Client.verifyIdToken` with the **iOS, Android, and web client IDs all accepted as valid audiences**, then routes into the same identity resolution as above so there stays exactly one place that creates users. Returns `{ accessToken, refreshToken, user }` as JSON — refresh token in the body because RN has no shared browser cookie jar. Add the native client IDs to the Zod schema in `config.module.ts`.

**3. Body-based refresh & logout fallback** — extend `POST /auth/refresh` and `POST /auth/logout` in `auth.controller.ts` to fall back to `req.body.refreshToken` when the cookie is absent. `AuthService.refresh()`/`logout()` already take a raw token string and are transport-agnostic, so only the controller's extraction needs a second branch. Cookie keeps priority; web is unchanged.

**4. Fix the missing `secure` cookie flag** — `setRefreshCookie` sets `httpOnly`/`sameSite`/`path`/`maxAge` but never `secure`. Add `secure: NODE_ENV === 'production'` so local HTTP dev still works. Pre-existing bug, worth fixing regardless.

**5. Rate limiting + `trust proxy`** — set `app.set('trust proxy', 1)` in `main.ts` **in the same change** as adding `@nestjs/throttler`. Caddy proxies every request, so without it `req.ip` is Caddy's container IP and the limiter becomes global rather than per-IP — locking out all users at once. Apply `@Throttle()` to the auth routes specifically rather than globally; map panning legitimately hammers the bbox and search endpoints and shouldn't share a budget with login.

**6. Sync correctness in `tracks.service.ts`:**
   - **Tombstones** — `listSince` currently filters `WHERE t."isActive" = true` (line 266), so a track deleted on one device never disappears from another. Return soft-deleted rows (at minimum `{id, isActive: false, updatedAt}`) so clients can reconcile.
   - **Bounded initial sync** — `listSince` is unpaginated, which is fine for deltas but unbounded on a fresh install where `since` is epoch. Add a cap plus continuation.

**7. `packages/api-types`** — new workspace, `packages/*` added to the root `workspaces` glob. Seed it with the shapes mobile needs first; migrating `apps/public`/`apps/admin` off their inline types can follow opportunistically rather than as a big-bang refactor.

**Deferred to Phase 7** (schema already accommodates them, so they're no longer retrofit risks): the Apple sign-in endpoint and UI, and `DELETE /api/v1/users/me`.

**Verification**: full manual login/refresh/logout pass on `apps/public` and `apps/admin` confirming no regression, then the new endpoints exercised via `curl` with a real Google ID token before any client code depends on them.

## Phase 1 — Scaffold + auth

1. **Scaffold** — `create-expo-app apps/mobile` (TypeScript), Expo Router for file-based navigation, mirroring the mental model TanStack Router already establishes in `apps/public`.
2. **Metro monorepo config** — `apps/public` pins `react@^19.2.0` and `apps/admin` `react@^19.2.7`, while Expo pins its own exact React. The repo uses pnpm workspaces, whose isolated linker gives each workspace's `node_modules/react` a symlink to that workspace's own declared version — no shared hoisted copy for Metro to resolve into. Still needs explicit `watchFolders` + `nodeModulesPaths` in `metro.config.js` so Metro can see `packages/api-types` and the rest of the monorepo. **Budget real time here** — this is the standard RN-in-a-monorepo tax and it is easier to fix before there's app code than after.
3. **API client** — `apps/mobile/src/lib/api.ts`, modeled on `apps/public/src/lib/auth/auth-fetch.ts` minus the SSR URL branching (mobile is always the "client" branch), pointed at `EXPO_PUBLIC_API_URL`. Send a client-version header from the start so the Phase 7 gate has something to read.
4. **Token storage** — access token in memory (same rationale as web), refresh token in `expo-secure-store`. On cold start, if a stored refresh token exists, mint an access token via the body-based `/auth/refresh`. Refresh tokens are single-use and rotating, so concurrent refreshes race — reuse the in-flight-promise dedupe that `apps/public/src/lib/auth/session.ts` already implements for exactly this.
5. **Login/logout** — `@react-native-google-signin/google-signin` (native sheet, no browser bounce; viable because dev builds are assumed) → `POST /auth/google/mobile`. Logout clears secure store and calls `/auth/logout` with the token in the body.
6. **NativeWind + palette tokens**, ported from `apps/public/src/styles.css`. Dark mode via `useColorScheme`.
7. **Sentry** wired up now, so every later phase reports crashes.

**Verification**: sign in with a real Google account on a physical device, land on an authenticated placeholder, cold-restart and stay signed in, log out cleanly.

## Later phases

Each gets its own planning pass when reached.

- **Phase 2 — Read-only browsing. Done.** Adventure pages, trails/spots, trip reports, guides, clubs/threads. Screens map roughly 1:1 from `apps/public/src/routes/*`. Establishes the navigation skeleton and UI primitives (Card/Button/Badge/EmptyState equivalents) before any write flows. Built as: `Stack.Protected`-gated navigation (`sign-in` vs. a `(tabs)` group — Discover/Guides/Clubs/Account — plus `adventures/[slug]` detail routes outside the tabs), React Query as the data-fetching layer (no existing pattern to mirror — `apps/public`'s TanStack Start loaders are SSR-specific), and `packages/api-types/src/content.ts` for the response shapes. One correction worth flagging for later phases: nothing in the API joins a display name onto an author/user reference — `TripReport`/`Comment`/`ThreadReply`/`GuideProfile` all return bare `authorId`/`userId`, resolved client-side via a `UserRef` component hitting `GET /users/:id/profile` (ported from `apps/public`'s `UserRef.tsx`). `Comment` and `ThreadReply` are also both nested one level server-side, not flat lists. Explicitly deferred to later phases: maps (no MapLibre until the Phase 3 spike — trail/spot lists render as text), the `ElevationProfile` chart, and every mutation (like/visit/kudos/join/reply/comment-post — those buttons simply aren't rendered yet).

- **Phase 3 — Offline. Done, at reduced scope (see below).** Two coupled tracks behind one "Download for offline" gesture on an adventure page: a **local SQLite content mirror** (page, trails, spots, elevation profiles) with a staleness/refresh policy, and **map tiles for that adventure's buffered bounding box**.
  **Spike resolved.** `maplibre-gl-js` supports `pmtiles://` through a JS protocol handler; the native SDKs behind `@maplibre/maplibre-react-native` do not — confirmed via MapLibre's own docs that PMTiles sources don't support offline pack downloads/caching in MapLibre Native at all. The fix: serve tiles as plain HTTP `{z}/{x}/{y}.pbf` (via the `pmtiles` npm package's Range-Request reader) so MapLibre Native's standard `OfflineManager` can bbox-download against them like any other tile source — no `pmtiles://` client protocol involved. **But the Nepal OSM-extract PMTiles archive this depends on doesn't exist anywhere in this repo** — CLAUDE.md named it as an intent, not a built asset — so building/sourcing it (planetiler/tippecanoe + a hosting decision) is a separate side-task, not code.
  **Scope cut, agreed with the user**: rather than block this phase on that archive, the map screen shipped against a free, no-API-key hosted vector tile source ([OpenFreeMap](https://openfreemap.org) — matches the "free, no API key" ethos already locked in for the web app's Leaflet+OSM setup), and the SQLite content mirror shipped in full. **Self-hosted PMTiles, the `apps/api` tile-serving route, and real offline map-pack downloads are deferred** to a later pass once the archive exists — today's "Download for offline" downloads page/trail/spot/elevation content only, not map tiles.
  **Built as**: `expo-sqlite` (JSON-blob-per-row tables keyed by adventure page, mirrors `packages/api-types` shapes directly rather than a normalized schema — the only query pattern needed is "give me everything for adventure X"), `@react-native-community/netinfo` for connectivity-aware cache-first reads in the existing `useAdventurePage`/`useTrails`/`useSpots` hooks (extended in place, not forked — screens didn't change), and `@maplibre/maplibre-react-native` v11 (a recent rewrite — its real API is `Map`/`Camera`/`GeoJSONSource`/`Layer`, not the `MapView`/`ShapeSource`/`LineLayer` names older tutorials use). Two build-time gotchas worth remembering: MapLibre Native has no web target at all (crashes Metro's web export at module-load, not just a graceful runtime no-op like Google Sign-In's web stub) — fixed with a `.web.tsx` platform-split stub (`AdventureMap.web.tsx`); and `expo-sqlite`'s web implementation needs `.wasm` added to Metro's `resolver.assetExts` or `expo export --platform web` fails outright.
  **Phase 2 bugs caught while wiring this in**: the `Trail`/`Spot` types in `packages/api-types/src/content.ts` had an invented `difficultyLevel` field on `Trail` (doesn't exist on that model) and a wrongly-nested `spotType: {name}` object on `Spot` (the API actually returns a flat `spotTypeName` string) — both fixed while adding the geometry/elevation fields this phase needed anyway.

- **Phase 4 — GPS recording.** Foreground first, then background. Sampling must be **distance-filtered and adaptive**, not time-based — naive 1 Hz GPS drains a phone in ~5 hours, shorter than a day hike. Requires `UIBackgroundModes: location` with a specific purpose string, Android's separate `ACCESS_BACKGROUND_LOCATION` flow and Play Console declaration, and a visible ongoing indicator. Background location is the most review-scrutinized permission there is; recording a hike justifies it, but the paperwork is real.
  Local SQLite outbox syncs via `POST /activity-tracks` with `clientUuid` idempotency — `@@unique([userId, clientUuid])` + `ON CONFLICT DO NOTHING` is already built for exactly this retry pattern — and the now-tombstone-aware `GET /me/activity-tracks?since=`. **Unit-test the sync reducer** (outbox, retry, tombstone reconciliation); this is the one place where the failure mode is silent data loss.

- **Phase 5 — Contribute/write flows.** Page/trail/spot create and edit through the same approval-pipeline endpoints the web uses (no new backend logic, only new UI), trip reports, club/thread posting, kudos/comments. Native camera via `expo-image-picker`, with `expo-image-manipulator` transcoding HEIC→JPEG and downscaling before upload — required, since the API whitelists only `jpeg|png|webp|gif` at 5MB and iOS shoots HEIC by default.

- **Phase 6 — Push notifications. Done.** Sender is the **Expo Push Notification Service** (`expo-server-sdk` backend, `expo-notifications` client), not raw FCM/APNs as originally worded above — Expo proxies both, so no Firebase project or APNs auth key was needed for a solo-dev app; confirmed with the user before building. Two new tables (`DeviceToken` — hard-deleted on unregister or an Expo `DeviceNotRegistered` receipt, not soft-deleted; `NotificationPreference` — one row per user, four flat booleans, not a category join table, since the category set is small and fixed) and a `NotificationCategory` grouping (`apps/api/src/notifications/notification-category.ts`) mapping all 16 `NotificationType` values into `SOCIAL`/`CONTRIBUTIONS`/`MODERATION`/`CLUBS` via an exhaustive `Record`, so a future `NotificationType` addition is a compile error until categorized. `PushService` (`apps/api/src/notifications/push.service.ts`) is called fire-and-forget (`.catch()`-wrapped, never awaited) from the end of `NotificationsService.notify()`/`notifyMany()` — push delivery can never add latency to or break the approval/report/comment flow that triggered it, same rule that already governed in-app notification firing. A `push.enabled` `SystemSetting` is the admin kill switch. New endpoints: `POST`/`DELETE /device-tokens` (body-based, not a URL param — Expo tokens contain `[`/`]`/`:`) and `GET`/`PATCH /notification-preferences` (get-or-default, no row forced into existence just to read it).
  On mobile: `src/lib/notifications/handler.ts` (side-effect module, same "register before the OS can need it" convention as `location-task.ts`) sets the foreground notification handler and Android channel; `src/lib/notifications/push.ts` holds `registerForPushNotificationsAsync()` plus two hooks — `usePushRegistration()` (registers on `status === 'signed-in'`, covering both fresh login and cold-start session restore; unregisters on the signed-in → signed-out transition) and `useNotificationTapHandler()` (passes a tapped notification's `linkUrl` straight to `router.push`, no translation table — backend `linkUrl` values are web-relative paths that mirror Expo Router's file-based paths in the common cases per the Phase 2/5 precedent). Preferences UI is a new "Notifications" section on the Account tab (four `Switch` rows, no new component — four fixed toggles didn't warrant one). `expo-notifications` needed no `.web.tsx` platform-split stub — unlike MapLibre/SQLite in Phase 3, it's web-safe out of the box and `expo export --platform web` passed clean on the first try.
  **Left for the user**: there is no `eas.json`/`extra.eas.projectId` in this repo — `getExpoPushTokenAsync` needs one, which requires `eas init`/`eas login` against the user's own Expo account (can't be provisioned non-interactively on their behalf). `registerForPushNotificationsAsync()` logs a warning and no-ops (doesn't throw) when the project id is absent, so the rest of the app is unaffected until that's run. Real push delivery, the account-tab toggle UX, and permission-prompt behavior all need the same physical-device pass flagged for every prior phase.

- **Phase 7 — Release readiness. In progress.** EAS Build/Submit pipeline with signing credentials — entirely separate from the existing GH Actions → SSH → compose flow. **Decided**: the moderator review-queue stays off mobile entirely — it's a staff tool, `apps/admin` already covers it, and every other admin-only surface (verification PATCH, thread pin/lock) was already deferred from Phase 5 on the same reasoning.
  **In-app account deletion — done** (App Store Guideline 5.1.1(v)). `UsersService.deleteOwnAccount` (`DELETE /users/me`) is soft-delete + anonymize in one `$transaction`, not a hard delete — `TripReport.authorId` is `Restrict` and `PageRevision`/`TrailRevision`/`SpotRevision` all carry `editorId`, so a real delete would tear holes in the wiki's revision history and block deleting content a departed user created. It deletes `RefreshToken`/`DeviceToken`/`AuthIdentity` rows outright (nothing to anonymize, no reason to linger), hard-deletes `ActivityTrack`s (private personal data, `userId` FK is `Cascade` for exactly this — the one exception to "anonymize, don't delete"), sets `Profile.name = '[deleted user]'` + clears `avatarUrl`, and overwrites `User.email`/`username` with a value deterministic from the (already-unique) user id — `deleted_<first-22-hex-chars-of-the-uuid>` — so a retried call is idempotent rather than colliding on the unique constraints. Content the account created (revisions, trip reports, comments, confirmations) stays exactly where it was, now attributed to "[deleted user]". The route lives on `UsersController` (`DELETE /users/me`, matching CLAUDE.md's `DELETE /api/v1/users/me` naming) but clears the shared refresh cookie via a new `apps/api/src/auth/refresh-cookie.ts` (hoisted out of `AuthController`, which previously held those constants privately) — same "stop sending a now-pointless cookie" reasoning as `AuthController.logout`. Mobile: `deleteAccount()` in `src/lib/auth/session.ts` (calls `DELETE /users/me` then clears the local token store/secure-store, mirroring `logout()`), wired into `AuthContext` as `deleteAccount`, and a destructive "Delete account" button on the Account tab behind an `Alert.alert` confirm — same pattern already used for discarding a GPS recording in `tracks/record.tsx` — whose copy explicitly tells the user their trip reports/edits/comments are retained under "[deleted user]" rather than removed, so the irreversible action isn't a surprise. No web/admin UI for this — Apple's requirement is iOS-app-specific, and there's no existing account-settings surface on `apps/public` to hang it off yet.
  **Apple sign-in — done** (endpoint + iOS UI + account linking). Backend: `apps/api/src/auth/apple-identity.ts` verifies the native `AuthenticationServices` identity token server-side via `jose`'s `createRemoteJWKSet`/`jwtVerify` against Apple's own JWKS (`https://appleid.apple.com/auth/keys`), checking `iss`/`aud`/`exp` — no passport strategy needed, since (unlike Google) there's no browser-redirect flow for Apple on this app; it's only required for the iOS app itself. `AuthService.handleAppleMobileLogin` mirrors `handleGoogleMobileLogin` exactly, routing through the same `loginWithIdentity`/`resolveIdentity` auto-link-on-verified-email path. New `APPLE_BUNDLE_ID` env var (optional, mirrors the `GOOGLE_IOS_CLIENT_ID` pattern) is the identity token's expected audience for a native app — `app.json` needed an explicit `ios.bundleIdentifier` added for the first time (`com.dolposcript.mobile`, matching the Android package) since nothing had set one yet, plus `ios.usesAppleSignIn: true` and the `expo-apple-authentication` config plugin.
  **The private-relay linking gap CLAUDE.md flagged** — an Apple "Hide My Email" address never matches an existing Google account's real email, so `resolveIdentity`'s auto-link can't fire for it — is solved with a separate authenticated `POST /auth/link/apple` (`AuthService.linkAppleIdentity`: attaches Apple as a second `AuthIdentity` on the caller's own account, 409s if that Apple ID is already linked to someone else) plus a small `GET /auth/identities` (`{ providers: AuthProvider[] }`) so the UI can render actual linked state rather than guessing from session-only memory. Mobile: `src/lib/auth/apple-signin.ts` wraps `expo-apple-authentication` (`isAvailableAsync`/`signInAsync`, iOS-only — the module is web/Android-safe to import out of the box, no `.web.tsx` stub needed, unlike MapLibre/SQLite in Phase 3), `sign-in.tsx` renders Apple's own branded `AppleAuthenticationButton` (Apple's HIG requires it, not a generic styled button) gated behind `isAppleSignInAvailable()`, and the Account tab gained a "Connected accounts" card (`useAuthIdentities`/`useLinkAppleIdentity` in `src/lib/resources/auth-identities.ts`) that only renders on iOS and shows "Linked" vs. a "Link Apple ID" button per provider.
  **Not built in this pass**: Apple's "first-authorization-only" `fullName` is threaded through (`AppleMobileLoginDto.fullName`, captured client-side from `credential.fullName` since it's never in the identity token and never resent on a later sign-in), but there's no re-prompt or backfill if a user's very first authorization is denied that scope — matches the Google flow's own no-retry behavior on a missing name. `tsc`/`expo lint`/`expo export --platform web`/`jest` all clean; real device verification (the native Apple sheet, HIG button rendering, and an actual private-relay linking flow) still needs a physical iOS device + Apple Developer account/entitlement, same as every other phase's device-only checklist.
  **Min-version gate — done.** A new `mobile.minVersion` `SystemSetting` (public, default `1.0.0`) is the live source of truth. Server: `apps/api/src/settings/min-version.middleware.ts`, applied to every route via `AppModule.configure()` (not a guard — it has to run ahead of `JwtAuthGuard` so a stale client is blocked from sign-in itself, not just already-authenticated routes) — compares the `X-Client-Version` header (already sent on every mobile request since Phase 1, previously unread) against the setting with a hand-written x.y.z comparator, 426s anything older with `{ minVersion }` in the body, and fails open (lets the request through) on a missing header or an unparseable version rather than risking a global lockout from a typo'd setting value. Web/admin never send the header, so this is a mobile-only gate. Mobile: `src/lib/version-gate.ts`'s `useVersionGate()` hook does a one-time unauthenticated `GET /settings/public` check on launch (fails open on a network error — offline shouldn't look like a stale-client block) and `_layout.tsx` renders `UpdateRequiredScreen` instead of the whole app (no tab chrome, no sign-in screen) when blocked, keeping the splash screen up until the check resolves either way. `checkUpgradeRequired()` is also called after every `authFetch` call and each of `session.ts`'s three raw-`fetch` auth calls, so a `mobile.minVersion` bump made *while* the app is already running still blocks it via a module-level flag, not just on cold start. `UpdateRequiredScreen` links out to `EXPO_PUBLIC_IOS_STORE_URL`/`EXPO_PUBLIC_ANDROID_STORE_URL` (both unset today, same "logs/degrades rather than throws" treatment as the missing EAS project id in Phase 6) and falls back to text-only instructions until the app is actually published. `tsc`/`expo lint`/`expo export --platform web` clean on both apps. Verified end-to-end against a running docker-compose stack: bumped `mobile.minVersion` at runtime and confirmed the API immediately 426s a client sending the old version (both on a plain route and on `/auth/google/mobile`, so sign-in itself is blocked), confirmed a missing/malformed header fails open, and confirmed the client-side `compareVersions`/gate logic resolves the same real API responses correctly — reverted the setting back to `1.0.0` afterward. The one thing not yet verified is the actual `UpdateRequiredScreen` render on a physical device/simulator (the host's Expo web dev server has an unrelated pre-existing React/react-dom version mismatch blocking that specific path).
  **Search parity — done**, scoped down after auditing what "parity" actually meant: Discover's adventure-page search and the Clubs tab's club-name search already ported 1:1 from `apps/public` in earlier phases (same debounced-`TextInput` → `/adventure-pages/search`/`GET /clubs?search=` pattern) — no gap there. Guides has no keyword search on either client, matching the API (no `search`/`q` endpoint exists for guide profiles, so there's nothing to port). The one real gap: `apps/public`'s `AttachmentPicker.tsx` (a search-as-you-type combobox over the three narrow `search?q=` stopgap endpoints plus `adventure-pages/search`, used to attach an optional `TripReport`/`Trail`/`Spot`/`AdventurePage` to a club thread) had no mobile equivalent — `clubs/[clubId]/threads/new.tsx` only had tag+content fields. Built `src/components/AttachmentPicker.tsx`, a direct RN port (inline results list below the `TextInput` instead of an absolutely-positioned overlay — RN has no reliable z-index-over-siblings story without a portal, so results just push the rest of the form down) and wired all four picker instances into the thread composer, matching `apps/public`'s one-of-each-type shape and `CreateThreadRequest`'s existing `tripReportId`/`trailId`/`spotId`/`adventurePageId` fields (already in `packages/api-types`, unused until now). No trip-groups screen exists on mobile at all yet (a separate, larger gap than "search" - the web `AttachmentPicker` also backs a "start a group" flow that has no mobile screen to attach to), so that's out of scope here, not silently dropped. `tsc`/`expo lint`/`expo export --platform web` clean; all four search endpoints hit directly against the live API to confirm the two response shapes (`{data:[...]}` for `adventurePage`, a bare array for the other three) match what the component parses.
  **i18n wiring — done.** `i18next`/`react-i18next` (`^26.3.6`/`^17.0.11`, matching `apps/public`'s versions) added to `apps/mobile`; `src/lib/i18n.ts` mirrors `apps/public/src/lib/i18n/index.ts`'s setup (`lng: 'en'`, `defaultNS: 'common'`, `useSuspense: false`, all namespaces statically imported since only `en` ships) minus the SSR/cookie locale-resolution half of that file (`locale.ts`) — no server render on mobile, so `lng` is just hardcoded rather than resolved per-request. ## Why these decisions (audit findings)

Kept for future reference — the reasoning behind the non-obvious calls above.

**Store-mandated, and the reason Phase 0 touches the schema at all:**
- **Sign in with Apple is required** (App Store Guideline 4.8) whenever third-party social login is the primary auth. Google Sign-In doesn't satisfy the exemption criteria — no email masking. This contradicts CLAUDE.md's locked "Auth is Google OAuth only" decision. The `AuthIdentity` table was chosen over a nullable `appleId` column specifically because it lets one user hold both providers, which is what makes the private-relay linking flow possible at all.
- **In-app account deletion is required** (Guideline 5.1.1(v)). There is no delete route today. It's non-trivial because `TripReport.authorId` is `Restrict` and revisions carry `editorId` — a hard delete would tear holes in the wiki's revision history, hence anonymize-and-retain.

**Correctness issues found in existing code:**
- `main.ts` never sets `trust proxy`, which would have turned a naively-added throttler into a global lockout.
- `listSince` filters `isActive = true`, so track deletions never propagate between a user's devices.
- `listSince` is unpaginated — fine for deltas, unbounded on first install.
- The uploads MIME whitelist omits `image/heic`, so iOS camera uploads would fail out of the box.

**Structural:**
- Expo cannot run in the Docker dev setup — the iOS Simulator needs a macOS host with Xcode, the Android emulator needs host virtualization, and Metro serves devices over the LAN. `apps/mobile` is the first deliberate exception to "full container dev"; the API stays containerized and mobile talks to it over a LAN IP.
- There is no `packages/` directory today; API shapes are declared inline per route (e.g. `interface ClubsSearch` in `apps/public/src/routes/clubs/index.tsx`). Mobile would have been a third hand-maintained copy, hence `packages/api-types` now, while there's only one new consumer.
- Offline *content* was the largest omission in the first draft of this plan. A basemap tells a trekker where they are; the actual value on the Annapurna circuit is the route description and safety notes, which live in Postgres.

## Verification approach

- Phase 0 is backend-only: confirm **no regression** on the existing web apps first, then exercise the new endpoints directly.
- Phase 1 onward runs on a physical device or simulator against the dockerized API (`docker-compose up`) over the host's LAN IP — remembering `apps/mobile` itself runs on the host.
- Repo convention is manual verification with no test suite; the single exception is unit tests around offline sync logic.
